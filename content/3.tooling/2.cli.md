`@mavonengine/cli` provides the `mavonengine` command. It requires **Node 24** or newer.

```bash
npm install -D @mavonengine/cli
npx @mavonengine/cli --help
```

## `mavonengine create`

Creates a new project from the multiplayer template, installs its dependencies and starts it like `mavonengine dev`.

```bash
npx @mavonengine/cli create my-game
```

Asks for a name if none is given, and puts the game's name, made from it (`my-game` → `My Game`), as [`appName`](/tooling/plugins#mavonenginejson) in `mavonengine.json`. A startup screen shows each step; then the dev script starts, the dashboard takes over as soon as the game server answers, and the game opens in the browser. It replaces `@mavonengine/create-bootstrap`, which now forwards to it.

| Option | Default | |
| --- | --- | --- |
| `--cwd <dir>` | current directory | Where to create the project directory |
| `--no-dashboard` | | Print the progress instead of showing the dashboard |
| `--port <port>` | `8050` | Game server HTTP port for the dashboard |
| `--theme <name>` | `dark` | Dashboard theme |
| `--transparent` | | Let a transparent terminal background show through |
| `--no-open` | | Don't open the game in the browser once the server is up |

## `mavonengine dev`

Runs the dev script of the project you are in and shows the [dashboard](/tooling/monitoring) for it. For the multiplayer template that starts the game server and the client together; its `npm run dev` is `mavonengine dev`.

```bash
npx @mavonengine/cli dev

# From somewhere else
npx @mavonengine/cli dev --cwd path/to/my-game
```

- Runs the project's `dev:server` script, or `dev` when there is none.
- The project root is the nearest `package.json` upwards that depends on `@mavonengine/core` and has a `dev` script, so it also works from inside `client/` or `server/`.
- The package manager comes from the lockfile (`npm`, `pnpm`, `yarn` or `bun`).
- Once the server is up, the game opens in the browser; `o` opens it again. `q` or `Ctrl-C` stops the dev script and everything it started.

Takes the same options as `create`.

### Installing plugins while it runs

`mavonengine dev` can install packages into the project and restart the dev servers afterwards, so a new plugin is loaded without stopping anything yourself:

- from the dashboard's **Plugins** tab, with `i` on a plugin that is available to install;
- from the [editor's](/core-concepts/level-editor#server-and-plugins-views) **Plugins** view, with the Install button of an available plugin, or by typing any package (a name, `name@version`, a `file:` path or a URL) into "Another package".

Both ask first and point at the package's source: installing a package runs its code on your machine, and nothing reviews what you install. The install is the same as `mavonengine install --yes`, followed by a restart of the dev script.

The editor's install requests are only taken from localhost and from the game's own page, so another site open in the browser can't install anything. Version ranges such as `^1.0.0` are refused there; use the terminal for those.

## `mavonengine plugins`

Lists the plugins that are available to install, and inside a project marks the ones already in its `mavonengine.json`.

```bash
npx @mavonengine/cli plugins
```

The list is [`plugins.json`](https://github.com/MavonEngine/Core/blob/main/plugins.json) in the MavonEngine repository, read from the `main` branch on GitHub every time the command runs. See [Available plugins](/tooling/plugins#available-plugins).

| Option | Default | |
| --- | --- | --- |
| `--json` | | Print the list as JSON |
| `--url <url>` | `$MAVONENGINE_PLUGINS_URL` | Read the list from somewhere else, such as a fork or a branch |

## `mavonengine install`

Installs packages with the project's package manager. For each one that is a MavonEngine [plugin](/tooling/plugins), it shows where the plugin runs and which prefabs it brings, and asks whether to add it to `mavonengine.json`.

```bash
npx @mavonengine/cli install @mavonengine/http-monitoring

# Anything your package manager takes
npx @mavonengine/cli install @acme/forest@^2 file:../my-plugin --yes
```

| Option | Default | |
| --- | --- | --- |
| `--cwd <dir>` | current directory | Where to start looking for the project |
| `-y`, `--yes` | | Add plugins to `mavonengine.json` without asking |
| `--no-register` | | Only install |

## `mavonengine make:plugin`

Creates a [plugin](/tooling/plugins#writing-a-plugin) inside the project you are in, ready to load:

```bash
npx @mavonengine/cli make:plugin forest
npx @mavonengine/cli make:plugin @acme/forest --target server
```

It writes `plugins/<name>/` (without the scope). That directory has a `package.json` with the `mavonengine` manifest, `src/client.ts` and/or `src/server.ts` with every hook stubbed, a `tsconfig.json` and a README. Then it:

- adds `plugins/*` to the `workspaces` in `package.json` (with pnpm, it adds a `link:` dependency instead);
- adds the plugin to `mavonengine.json`;
- runs the package manager's install, which links the plugin into `node_modules`.

The manifest points at the TypeScript sources, so there is no build step. Vite compiles the client entry, and Node 24 strips the types from the server entry. Because of that, the server entry can only use syntax Node can strip (no `enum`s or parameter properties), and it imports its own files with `.ts` extensions. The generated `tsconfig.json` enforces both. The client reloads when its entry changes; restart the game server after changing the server entry. To publish the plugin to npm later, build it to `dist/` like the [first-party plugins](https://github.com/MavonEngine/Core/tree/main/packages/plugins) and point the manifest there.

It refuses a name that is already in `mavonengine.json` or installed, or whose directory exists, and it never overwrites a file.

| Option | Default | |
| --- | --- | --- |
| `--target <side>` | `both` | `client`, `server` or `both` |
| `--cwd <dir>` | current directory | Where to start looking for the project |
| `--no-register` | | Leave `mavonengine.json` alone |
| `--no-install` | | Don't run the package manager to link it |

## `mavonengine asset:publish`

Copies the files a plugin lets you change into your project, such as the [mail plugin's layout](/tooling/mail#layout):

```bash
npx @mavonengine/cli asset:publish @mavonengine/mail
```

They go to `resources/<package>/`, here `resources/@mavonengine/mail/layout.html`. The plugin uses your copy from then on, so change it there and commit it. Files you have already are kept, so publishing again after an update only adds the plugin's new files. `--force` replaces yours with the plugin's.

A plugin offers files with `publish` in its manifest, see [Files a project can change](/tooling/plugins#files-a-project-can-change).

| Option | Default | |
| --- | --- | --- |
| `--cwd <dir>` | current directory | Where to start looking for the project |
| `--force` | | Replace the files you have with the plugin's |

## `mavonengine build`

Runs the project's `build` script, then lists what each plugin put into the release. Only the shared plugin assets and those of the prefabs listed in `mavonengine.json` are copied, so a release never ships, or requests, a file it doesn't use.

```bash
npx @mavonengine/cli build
```

## `mavonengine doctor`

Checks the project you are in and tells you what to do about each problem it finds. It changes nothing.

```bash
npx @mavonengine/cli doctor
```

```
MavonEngine project at ~/games/my-game (npm, @mavonengine/core 0.0.25)

Environment
  ✓ Node 24.4.0                 needs >=24
  ✓ @mavonengine/cli 0.0.6
  i @mavonengine/core 0.0.25    0.0.26 is out

mavonengine.json
  ✓ mavonengine.json  2 plugins
  ✗ appUrl "mygame.com"         is not an http(s) URL
      → e.g. "appUrl": "https://mygame.com"

Plugins
  ✓ @mavonengine/chat 0.0.3     core >=0.0.22
  ✗ @mavonengine/auth 0.2.0     made for @mavonengine/core >=0.0.26, the project has 0.0.25
      → mavonengine install @mavonengine/auth@0.1.1

2 errors, 0 warnings
```

- **Environment**: the Node version, compared with what the CLI and the installed `@mavonengine/core` need. Then, for each `@mavonengine/*` package in `package.json`: whether it is installed and matches the range there (or `npm install` is due), and whether a newer version is out.
- **mavonengine.json**: whether the file can be read, an `appUrl` that isn't an http(s) URL, a `database`, `auth` or `notifications` that names a plugin that isn't in `plugins` or is turned off, entries of the wrong shape, and settings it doesn't know (typos).
- **Migrations**: the [`upgrade`](#mavonengine-upgrade) migrations in the project's core that the project hasn't had yet.
- **Plugins**: each plugin in `mavonengine.json` must be installed, be a MavonEngine plugin and be built (its entries exist). The assets of the prefabs in use must be there, and the plugin must be made for the project's core. A plugin's supported core is `engine` in its [manifest](/tooling/plugins#writing-a-plugin), or else its `@mavonengine/core` peer dependency. When a plugin doesn't fit, doctor looks through the versions published on npm and names the newest one that does. It also points out plugins that are installed but not in `mavonengine.json`.

The game server and the Vite plugin check `engine` too when they load plugins. A plugin made for another core still loads, with a warning that points to `mavonengine doctor`.

Version lookups go to the npm registry (`npm_config_registry` when set, otherwise registry.npmjs.org) and send it the names of the project's `@mavonengine/*` packages and plugins. `--offline` skips them. When the registry can't be reached, doctor gives one warning and checks the rest anyway.

The exit code is 1 when something is wrong (✗) and 0 otherwise. With `--strict`, warnings (!) fail too; notes (i) never do. `--json` prints the findings for CI and scripts.

| Option | Default | |
| --- | --- | --- |
| `--offline` | | Don't ask the npm registry |
| `--strict` | | Fail on warnings too |
| `--json` | | Print the findings as JSON |
| `--cwd <dir>` | current directory | Where to start looking for the project |

## `mavonengine upgrade`

Moves the project to the latest `@mavonengine/core`, with plugins that work with it, then makes the changes to the project's files that the new core needs.

```bash
npx @mavonengine/cli upgrade --dry-run   # see what would happen
npx @mavonengine/cli upgrade
```

1. **Packages.** `@mavonengine/core` goes to its latest version on the npm registry, or to `--to <version>`. Each plugin goes to its newest version whose `engine` range takes that core. The other `@mavonengine/*` packages go to their newest version whose `@mavonengine/core` peer range takes it. Nothing is downgraded, and packages from `file:`, git or another source are left alone. When a plugin has no version for the new core, the upgrade stops before installing anything; pick an older core with `--to`, remove the plugin, or pass `--force`. The project's package manager installs the packages. Each one stays in `dependencies` or `devDependencies`, and pinned versions stay pinned.
2. **Migrations.** These come from the newly installed core, so the new core decides what to migrate. Each one is shown as a diff before anything is written. Applied migrations are recorded in `migrations` in `mavonengine.json` and are never offered again, even if you undo one on purpose. When a migration adds a dependency, the package manager installs it.
3. **Doctor.** [`mavonengine doctor`](#mavonengine-doctor) checks the result, and the exit code is doctor's.

| Migration | What it changes |
| --- | --- |
| `0.0.22-dev-script` | `npm run dev` starts `mavonengine dev`. The old `dev` script becomes `dev:server`, and `@mavonengine/cli` becomes a dev dependency |
| `0.0.25-app-name-title` | `index.html`'s `<title>` becomes `%MAVONENGINE_APP_NAME%`. The old title becomes `appName` in `mavonengine.json`, so the browser tab still shows the same name |

The upgrade asks before installing and before writing. `--yes` skips both questions, and it is required when there is no terminal. It won't start with uncommitted changes in git, so you can review and undo its changes on their own; `--allow-dirty` overrides that. If you installed the packages yourself, `--only-migrations` runs only steps 2 and 3.

| Option | Default | |
| --- | --- | --- |
| `--to <version>` | latest | The `@mavonengine/core` version to move to |
| `--only-migrations` | | Leave the packages alone |
| `--dry-run` | | Show what would happen, change nothing |
| `-y`, `--yes` | | Don't ask |
| `--force` | | Upgrade even when a plugin has no version for the new core |
| `--allow-dirty` | | Start with uncommitted changes |
| `--cwd <dir>` | current directory | Where to start looking for the project |

## `mavonengine dashboard`

A live terminal dashboard for a running game server, see [Monitoring](/tooling/monitoring). With a [database plugin](/tooling/database) it gets a Database tab; pass the server's admin token as `--token` to read it on a server that has one.

```bash
npx @mavonengine/cli dashboard
npx @mavonengine/cli dashboard --sim   # simulated data, no server needed
```
