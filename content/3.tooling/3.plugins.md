An engine plugin is an npm package that adds code to the client, the game server or both, and can bring prefabs and assets. Install one with the [CLI](/tooling/cli):

```bash
npx @mavonengine/cli install my-custom-plugin
```

## Available plugins

The official plugins are listed in [`plugins.json`](https://github.com/MavonEngine/Core/blob/main/plugins.json) at the root of the MavonEngine repository:

| Plugin | Runs on | |
| --- | --- | --- |
| [`@mavonengine/http-monitoring`](/tooling/monitoring#browser-dashboard) | server | The game server dashboard in the browser, as a page of the [admin panel](/tooling/admin-panel) |
| [`@mavonengine/chat`](/tooling/chat) | client and server | In-game text chat with rate limiting, mutes, proximity chat and an admin API |
| [`@mavonengine/sqlite`](/tooling/database) | server | A SQLite database for the game server and its plugins, on Node's built-in `node:sqlite` |
| [`@mavonengine/auth`](/tooling/auth) | client and server | Player accounts with logins and sessions, so the game server knows who connects, and an accounts page in the admin panel |
| [`@mavonengine/mail`](/tooling/mail) | server | Mail from the game server, queued and retried, over SMTP or any nodemailer transport, with a dev inbox in the admin panel |
| [`@mavonengine/notifications`](/tooling/notifications) | client and server | Notify players in the game, by mail and kept to read later: `player.notify(new LevelUp())` |

`mavonengine plugins` prints the list, read from GitHub each time, so a new plugin shows up as soon as it is added. The same list appears, with what your project doesn't have yet, in:

- the **Plugins** tab of the [dashboard](/tooling/monitoring#terminal-dashboard), where `i` installs the selected plugin under `mavonengine dev`;
- the **Plugins** view of the [editor](/core-concepts/level-editor#graphs-server-and-plugins-views), which also shows each plugin's readme and installs any other package;
- the `available_plugins` tool of the [MCP server](/tooling/ai-assistants#plugin-tools), so an assistant can suggest a plugin instead of building what one already does.

Installing from the dashboard or the editor asks first, since a package's code runs on your machine, then adds the plugin to `mavonengine.json` and restarts the dev servers.

To list a plugin of your own, add an entry to `plugins.json`: `package` (the npm name) is required; `name`, `description`, `target`, `engine` (the supported `@mavonengine/core` range), `homepage` and `readme` (the URL of its README as Markdown) are optional.

## mavonengine.json

Enabled plugins are listed in `mavonengine.json` in the project root, next to `package.json`:

```json
{
  "appUrl": "https://mygame.com",
  "appName": "My Game",
  "plugins": {
    "my-custom-plugin": { "enabled": true, "prefabs": ["Tree"], "options": { "density": 2 } }
  }
}
```

| Field | Description |
|-------|-------------|
| `enabled` | `false` turns the plugin off without uninstalling it |
| `prefabs` | The plugin prefabs the project uses. The editor adds a prefab when you place it. Only these prefabs' assets (plus the shared ones) go into the release |
| `options` | Passed to the plugin as `ctx.options` |

Next to `plugins`, the file says what goes for the whole project. All of these are optional:

| Key | |
| --- | --- |
| `appUrl` | Where the game is, like `https://mygame.com`. Links that leave the game, such as those in [mails](/tooling/mail), point there. `MAVONENGINE_APP_URL` overrides it, for example per deployment. A production server never builds such links from the address a request names, so set it before deploying |
| `appName` | The game's name, in mails and in the browser tab: `%MAVONENGINE_APP_NAME%` in the client's `index.html` becomes it, in dev and in the build (`MavonEngine` without one). `mavonengine create` sets it from the project's name. Rebuild the client after changing it |
| `database` | The [database plugin](/tooling/database) to use, when more than one is enabled |
| `auth` | The [auth plugin](#authenticating-players) to use, when more than one is enabled |
| `notifications` | The [notifications plugin](/tooling/notifications) that `notify()` sends through, when more than one is enabled |
| `migrations` | The [`mavonengine upgrade`](/tooling/cli#mavonengine-upgrade) migrations the project has had, by id. `upgrade` writes it; leave it alone |

Without `database`, `auth` or `notifications`, the first plugin of that kind that is enabled is used. Server plugins get `appUrl` and `appName` as `ctx.appUrl` and `ctx.appName`; the server's `appUrl` and `appName` options win over the file.

The client reloads when the plugins change. Restart the game server to load a new server plugin.

## Setting up a project

Projects made with `mavonengine create` are already set up. For an existing project:

```typescript
// client: before new Game()
import Game from '@mavonengine/core/Game'
import plugins from 'virtual:mavonengine/plugins'

Game.usePlugins(plugins)
```

```typescript
// server: the directory with mavonengine.json
const server = new MyServer(logger, physicsWorld, { plugins: { root: projectRoot } })
await server.start()
```

The client's Vite config must extend `@mavonengine/core/vite.config`, which provides `virtual:mavonengine/plugins`, serves plugin assets in dev and copies them into the release.

## Writing a plugin

[`mavonengine make:plugin <name>`](/tooling/cli#mavonengine-makeplugin) sets one up inside your project, with every hook stubbed and nothing to build. A plugin is an npm package with a `mavonengine` field in its `package.json`:

```json
{
  "name": "my-custom-plugin",
  "type": "module",
  "mavonengine": {
    "target": "both",
    "client": "./dist/client.js",
    "server": "./dist/server.js",
    "dev": "./dist/dev.js",
    "engine": "^0.0.25",
    "publish": "./publish",
    "assets": {
      "dir": "./assets",
      "shared": ["textures/bark.png"],
      "prefabs": {
        "Tree": ["models/tree.glb"],
        "Rock": ["models/rock.glb"]
      }
    }
  }
}
```

- `target`: `client`, `server` or `both`. The matching entries are required.
- `assets`: paths relative to `dir` (default `assets`), served at `/plugins/<package>/<path>`. In dev all of them; in a release only the shared ones and those of used prefabs.
- `dev`: optional, for any target. An entry that runs in the client's Vite dev server, see [Dev entries](#dev-entries).
- `reloadOnOptions`: default `true`. Set it to `false` when the plugin changes its own `options` while the editor is open and its client picks up the change without a reload.
- `publish`: a directory of files the project may change, such as a mail layout, see [Files a project can change](#files-a-project-can-change).
- `engine`: the `@mavonengine/core` range the plugin is made for. A plugin outside the project's range still loads, with a warning that points to [`mavonengine doctor`](/tooling/cli#mavonengine-doctor), and [`mavonengine upgrade`](/tooling/cli#mavonengine-upgrade) uses it to pick the plugin's version for a new core. Without it, the plugin's `@mavonengine/core` peer dependency counts.

Each entry default-exports the plugin. Every hook gets the plugin's context last, with `package`, `options`, `game` and `logger`.

### Client

```typescript
import { defineClientPlugin } from '@mavonengine/core/Plugins/types'

export default defineClientPlugin({
  assets: ctx => [{ name: 'tree', type: 'gltfModel', path: ctx.assetUrl('models/tree.glb') }],
  setup(ctx) {
    ctx.registerPrefab({
      name: 'Tree',
      spawn: position => ({ object: new Tree(position) }),
    })
  },
  update(delta, ctx) {},
  // Connecting to the game server failed: status is the HTTP status it answered, undefined when it couldn't be reached
  onConnectError(error, ctx) {},
  // Dev only, when the editor boots
  editor(ctx) {
    ctx.editor.on('objectSelected', () => {})
  },
})
```

The client context also has `plugin()` to [use other plugins](#using-other-plugins), `registerSceneObject()` to add [scene object types](/core-concepts/scenes#scene-object-types) and `registerNode()` to add [graph nodes](#graphs-and-nodes). A client plugin can also give the token the game connects with, see [Authenticating players](#authenticating-players).

`onConnectError({ message, status })` is called on every client plugin when connecting to the game server fails, before the `NetworkManager`'s own `connectError` event. `status` is the HTTP status the server turned the client away with, such as 401 from its auth plugin, and undefined when the server couldn't be reached. For example, an auth plugin can use it to forget a session the server no longer accepts, so the next connection goes without it.

### Server

```typescript
import { defineServerPlugin } from '@mavonengine/core/Plugins/types'

export default defineServerPlugin({
  setup(ctx) {},
  // Runs after the server's own onHttp routes, before the game client
  http(app, ctx) {
    app.get('/api/my-plugin/status', (_req, res) => res.json({ ok: true }))
  },
  onConnection(channel, client, ctx) {},
  onDisconnect(channel, ctx) {},
  tick(delta, ctx) {},
  // May return a promise: the database is closed once it settled
  destroy(ctx) {},
})
```

The server context also has `server`, `projectRoot`, `appUrl`, `appName`, `registerSceneObject()`, `registerNode()`, `requireAdmin`, `adminToken`, `admin`, `db`, `table()`, `queue`, `identity()`, `plugin()` and `publishedFile()`. `ctx.queue` is the server's [job queue](/tooling/queue): register the plugin's job classes in `setup()`. Plugins reach the physics world through `ctx.game.physicsWorld`, see [Physics](/core-concepts/physics).

The routes a plugin registers are listed with its name on the dashboard's Routes and Plugins tabs. Say what they do with [`describeRoute()`](/networking/server#describing-routes).

### Graphs and nodes

A plugin can ship [material](/core-concepts/material-graphs) and [logic graphs](/core-concepts/logic-graphs): put `<name>.graph.json` files (made in the editor's Graphs view, then copied over) in a `graphs/` directory in the package. They go by `<package>:<name>`, e.g. `my-custom-plugin:ocean`, wherever a graph is picked: a primitive's material graph, a Logic Graph object's graph. They are served at `/graphs/<package>/<name>.graph.json`, shipped in every release, and the server reads them from the package. The editor lists them read-only; *Copy to project* makes an editable copy. A plugin can ship only graphs.

It can also add node types from `setup`. Their key in graph files is `<package>:<type>`, which `registerNode` returns. Material nodes take their TSL implementation as a second argument; logic nodes need registering in the server entry too, for graphs that run there:

```typescript
// client.ts
import { defineClientPlugin } from '@mavonengine/core/Plugins/types'
import { sin, time } from 'three/tsl'

export default defineClientPlugin({
  setup(ctx) {
    ctx.registerNode({
      type: 'wobble',
      label: 'Wobble',
      category: 'Math',
      kinds: ['material', 'logic'],
      inputs: {
        speed: { type: 'float', default: 1 },
      },
      outputs: {
        value: { type: 'float' },
      },
      // In logic graphs
      eval: ({ speed }, { time }) => ({
        value: Math.sin(time * Number(speed)),
      }),
    }, ({ speed }) => ({
      // In material graphs: TSL
      value: sin(time.mul(speed)),
    }))
  },
})
```

### Dev entries

A plugin's `dev` entry runs in the client's Vite dev server, only in dev: tooling for the editor that has to work with the project's files, like downloading something and writing it into `client/public/`. It is never part of a build, and the game server never loads it.

```typescript
// dev.ts
import { mkdirSync } from 'node:fs'
import { defineDevPlugin } from '@mavonengine/core/Plugins/types'

export default defineDevPlugin({
  setup(ctx) {
    mkdirSync(ctx.dataDir, { recursive: true })
  },
  // Answers under /__mavonengine/plugins/<package>/, with that prefix taken off req.url
  middleware: ctx => (req, res, next) => {
    if (req.url !== '/status')
      return next() // 404
    res.setHeader('Content-Type', 'application/json')
    res.end(JSON.stringify({ options: ctx.options }))
  },
  destroy(ctx) {},
})
```

The client side calls it with `` fetch(`${devPluginBase(ctx.package)}status`) ``, using `devPluginBase` from `@mavonengine/core/Plugins/types`. Only requests from localhost reach the middleware, and requests that change something (anything but GET and HEAD) only when they come from the game's own page, so another site open in the browser can't make them. Paths in `req.url` come from the browser: resolve them with `resolveInside()` from `@mavonengine/core/Plugins/ProjectConfig` before reading or writing files.

The context has `package`, `options` (read from `mavonengine.json` on every access), `projectRoot`, `clientRoot`, `publicDir`, `logger`, and:

- `dataDir`: `.mavonengine/plugins/<package>/` in the project, for downloads and caches. The project's `.gitignore` leaves out `.mavonengine`, so nothing there is committed or shipped.
- `updateOptions(change)`: changes the plugin's `options` in `mavonengine.json`. Use it to record what should be committed with the project.

Dev entries start with the dev server and restart when plugins are added, removed, turned on or off in `mavonengine.json`. Changing options doesn't restart them. One that fails to start is logged, and its URLs answer 404 with the reason. Assets the plugin adds while the game runs can be loaded with [`resources.add()`](/resources#loading-more-assets-while-the-game-runs).

#### Tools for AI assistants

A dev entry can also give AI assistants tools, which [`mavonengine mcp`](/tooling/ai-assistants#project-plugin-tools) offers as `<plugin>_<tool>`: the package name without its scope, then the tool's name.

```typescript
export default defineDevPlugin({
  mcpTools: ctx => [
    {
      name: 'add_tree', // my-plugin_add_tree
      title: 'Add a tree',
      description: 'Adds a tree to the list in the plugin\'s options. Use it when the user asks for more trees',
      input: {
        type: 'object',
        properties: { kind: { type: 'string', enum: ['pine', 'oak'] } },
        required: ['kind'],
      },
      run: ({ kind }) => {
        ctx.updateOptions((options) => {
          options.trees = [...(options.trees as string[] ?? []), kind]
        })
        return { trees: ctx.options.trees }
      },
    },
  ],
})
```

- `input` is the JSON Schema of the arguments, an object; `mavonengine mcp` turns away calls that don't match it. The arguments still come from a model, so check them in `run()` as you would any input, e.g. paths with `resolveInside()`.
- What `run()` returns goes to the assistant as JSON. What it throws is reported as the tool's error.
- Set `readOnly: true` on tools that change nothing; the rest are taken to change something, so assistants ask first and `mavonengine mcp --read-only` leaves them out. `destructive: true` marks one that deletes or overwrites what can't be had back, `openWorld: true` one that reaches outside the project, e.g. a website.
- The dev server lists them on `GET /__mavonengine/mcp/tools` and runs them on `POST /__mavonengine/mcp/tools/<name>` with `{ "arguments": … }`, only for requests from this machine and never for another site open in the browser. A plugin can't take the name of one of the engine's own tools.

[`@mavonengine/mail`](/tooling/mail#with-an-ai-assistant) gives its dev inbox to assistants this way.

### Using other plugins

A plugin offers something to other plugins with `api()`, and they get it with `ctx.plugin('<package>')`. It is undefined when that plugin isn't installed, enabled or running, or has no api, so a plugin can work without the ones it can use:

```typescript
// @acme/shop: mails a receipt when the project has the mail plugin
export default defineServerPlugin({
  http(app, ctx) {
    app.post('/api/shop/buy', async (req, res) => {
      const order = await buy(req.body)
      await ctx.plugin('@mavonengine/mail')?.to(order.email).send(new Receipt(order))
      res.json(order)
    })
  },
})
```

```typescript
// @acme/leaderboard: offers its api
export default defineServerPlugin({
  api: ctx => ({
    top: (limit: number) => ctx.db!.selectFrom(ctx.table('scores')).selectAll().orderBy('score', 'desc').limit(limit).execute(),
  }),
})
```

`api()` is called once for every plugin, before any plugin's `setup()`, so a plugin can use another's api in its own `setup()` whatever order they load in. On the server it runs after the database migrations, so a plugin they turned off has no api. Client and server each have their own: a plugin's client api can differ from its server api.

To give `ctx.plugin()` the api's type, add it to `ServerPluginApis` (or `ClientPluginApis` in the browser):

```typescript
declare module '@mavonengine/core/Plugins/types' {
  interface ServerPluginApis {
    '@acme/leaderboard': LeaderboardApi
  }
}
```

[`@mavonengine/mail`](/tooling/mail), [`@mavonengine/notifications`](/tooling/notifications) and [`@mavonengine/auth`](/tooling/auth#on-the-server) offer theirs this way.

### Files a project can change

A plugin can let the project change some of its files, such as the layout of its mails. Put them in a directory of the package and name it as `publish` in the manifest. [`mavonengine asset:publish <package>`](/tooling/cli#mavonengine-assetpublish) copies them into the project's `resources/<package>/`, and the plugin finds the project's copy with `ctx.publishedFile()`:

```typescript
import { readFileSync } from 'node:fs'

const layout = readFileSync(ctx.publishedFile('layout.html') ?? new URL('../publish/layout.html', import.meta.url), 'utf8')
```

`publishedFile()` is undefined when the project has no copy, so the plugin uses its own.

### Admin routes

Guard a plugin's admin routes with `ctx.requireAdmin`, which asks for the server's [admin token](/networking/server#admin-token), instead of giving the plugin a token of its own:

```typescript
export default defineServerPlugin({
  http(app, ctx) {
    app.post('/api/my-plugin/reset', ctx.requireAdmin, (_req, res) => res.json({ reset: true }))
  },
})
```

A plugin that takes the token some other way, such as the password of a login, checks it with `ctx.adminToken.matches(candidate)`. `ctx.adminToken.configured` tells whether the server has one. The plugin never sees the token itself.

### Admin panel pages

A plugin adds pages to the server's [admin panel](/tooling/admin-panel) with `ctx.admin.page()`. They share its layout and login, and are listed in its sidebar under **Plugins**:

```typescript
export default defineServerPlugin({
  http(app, ctx) {
    ctx.admin.page({ path: 'chat', label: 'Chat', icon: 'chat', render: () => '<div class="adm-page">…</div>' })
    // Already behind the panel's login
    app.get(ctx.admin.url('chat/api/messages'), (_req, res) => res.json({ messages: [] }))
  },
})
```

See [Adding a page](/tooling/admin-panel#adding-a-page) for sub pages, scripts, styles and more logins.

### Database

With a [database plugin](/tooling/database) in the project, `ctx.db` is a [Kysely](https://kysely.dev) instance shared by the server and all plugins, and undefined without one. A plugin creates its tables with `migrations`, which run before `setup()`, and names them with `ctx.table()` so plugins' tables don't clash:

```typescript
export default defineServerPlugin({
  migrations: {
    '001_init': {
      async up(db, { table }) {
        await db.schema.createTable(table('scores'))
          .addColumn('player', 'text', c => c.primaryKey())
          .addColumn('score', 'integer', c => c.notNull().defaultTo(0))
          .execute()
      },
    },
  },
})
```

See [Database](/tooling/database#in-a-plugin) for the rules of migrations, and for the `database()` hook that makes a plugin a database plugin itself. Likewise, a `notify()` hook makes a plugin a [notifications plugin](/tooling/notifications#writing-a-notifications-plugin).

### Authenticating players

An auth plugin decides who may connect, before a client gets a player. [`@mavonengine/auth`](/tooling/auth) is one, with accounts, passwords and sessions; write your own for anything else. Its client entry gives the token the game connects with, and its server entry's `authorize()` checks it:

```typescript
// client.ts: sent as the Authorization header of the connection request
export default defineClientPlugin({
  authorization: () => {
    const token = localStorage.getItem('session')
    return token ? `Bearer ${token}` : undefined
  },
})
```

```typescript
// server.ts
export default defineServerPlugin({
  async authorize(authorization, request, ctx) {
    const account = await findSession(ctx.db, authorization)
    if (!account)
      return false // 401
    if (account.banned)
      return 403
    return { id: account.id, name: account.username }
  },
})
```

`authorize()` returns:

| Result | |
| --- | --- |
| An identity, `{ id, name?, … }` | Lets the client in as that account. It is also sent to the client, so keep it to what the player may see |
| `true` | Lets it in without an identity, e.g. as a guest |
| `false` | Turns it away with 401 |
| An HTTP status from 400 to 599 | Turns it away with that status, e.g. 403 for a banned account |

A throw or any other result turns that one client away with 500, and the next client is still asked.

- **Reading the identity:** other plugins use `ctx.identity(channel)`, the game `player.identity` on the server and `network.identity` on the client. Key anything that should outlast a connection, such as a mute or a score, on `identity.id`: `channel.id` changes every time the player reconnects.
- **Refusals on the client:** they arrive as the `connectError` event of the [`NetworkManager`](/networking/client#authentication), with the `status` the server answered. The token is read when a `NetworkManager` is made, so to connect again after logging in, make a new one.
- **One auth plugin:** only one is asked. With more than one enabled, set `"auth": "<package>"` in `mavonengine.json`.
- **Fails closed:** when the project has an auth plugin that doesn't run, for example because one of its migrations failed or the package named in `auth` isn't enabled, the server turns every client away with 503 instead of letting them in unchecked.
- **The editor** connects like a client, so with an auth plugin it needs a token as well. When the server turns it away, the editor's status bar and Network panel say why.

A hook that throws is logged and turned off for that plugin, and the game keeps running.
