`@mavonengine/cli` stellt den Befehl `mavonengine` bereit. Er benötigt **Node 24** oder neuer.

```bash
npm install -D @mavonengine/cli
npx @mavonengine/cli --help
```

## `mavonengine create`

Erstellt ein neues Projekt aus dem Multiplayer-Template, installiert seine Abhängigkeiten und startet es wie `mavonengine dev`.

```bash
npx @mavonengine/cli create my-game
```

Fragt nach einem Namen, wenn keiner angegeben ist, und trägt den daraus gebildeten Namen des Spiels (`my-game` → `My Game`) als [`appName`](/de/werkzeuge/plugins#mavonenginejson) in `mavonengine.json` ein. Ein Startbildschirm zeigt jeden Schritt; danach startet das Dev-Skript, das Dashboard übernimmt, sobald der Spielserver antwortet, und das Spiel öffnet sich im Browser. Es ersetzt `@mavonengine/create-bootstrap`, das jetzt dorthin weiterleitet.

| Option | Standard | |
| --- | --- | --- |
| `--cwd <dir>` | aktuelles Verzeichnis | Wo das Projektverzeichnis erstellt wird |
| `--no-dashboard` | | Fortschritt ausgeben, statt das Dashboard anzuzeigen |
| `--port <port>` | `8050` | HTTP-Port des Spielservers für das Dashboard |
| `--theme <name>` | `dark` | Dashboard-Theme |
| `--transparent` | | Einen transparenten Terminal-Hintergrund durchscheinen lassen |
| `--no-open` | | Das Spiel nicht im Browser öffnen, sobald der Server läuft |

## `mavonengine dev`

Führt das Dev-Skript des Projekts aus, in dem du dich befindest, und zeigt das [Dashboard](/de/werkzeuge/monitoring) dafür an. Beim Multiplayer-Template startet das Spielserver und Client gemeinsam; sein `npm run dev` ist `mavonengine dev`.

```bash
npx @mavonengine/cli dev

# Von woanders aus
npx @mavonengine/cli dev --cwd path/to/my-game
```

- Führt das `dev:server`-Skript des Projekts aus, oder `dev`, wenn es keines gibt.
- Der Projekt-Root ist die nächste `package.json` aufwärts, die von `@mavonengine/core` abhängt und ein `dev`-Skript hat — es funktioniert also auch aus `client/` oder `server/` heraus.
- Der Paketmanager wird anhand der Lockfile erkannt (`npm`, `pnpm`, `yarn` oder `bun`).
- Sobald der Server läuft, öffnet sich das Spiel im Browser; `o` öffnet es erneut. `q` oder `Ctrl-C` beendet das Dev-Skript und alles, was es gestartet hat.

Nimmt dieselben Optionen wie `create`.

### Plugins im laufenden Betrieb installieren

`mavonengine dev` kann Pakete ins Projekt installieren und danach die Dev-Server neu starten, sodass ein neues Plugin geladen wird, ohne dass du selbst etwas beenden musst:

- im **Plugins**-Tab des Dashboards, mit `i` auf einem Plugin, das zur Installation verfügbar ist;
- in der **Plugins**-Ansicht des [Editors](/de/kernkonzepte/level-editor#server-und-plugins), mit dem Install-Button eines verfügbaren Plugins oder indem du ein beliebiges Paket (einen Namen, `name@version`, einen `file:`-Pfad oder eine URL) bei „Another package“ eingibst.

Beide fragen vorher nach und verweisen auf den Quellcode des Pakets: Ein Paket zu installieren führt dessen Code auf deinem Rechner aus, und niemand prüft, was du installierst. Die Installation entspricht `mavonengine install --yes`, gefolgt von einem Neustart des Dev-Skripts.

Installationsanfragen des Editors werden nur von localhost und von der eigenen Seite des Spiels angenommen, eine andere im Browser geöffnete Website kann also nichts installieren. Versionsbereiche wie `^1.0.0` werden dort abgelehnt; nutze dafür das Terminal.

## `mavonengine plugins`

Listet die Plugins auf, die zur Installation verfügbar sind, und markiert innerhalb eines Projekts diejenigen, die bereits in dessen `mavonengine.json` stehen.

```bash
npx @mavonengine/cli plugins
```

Die Liste ist [`plugins.json`](https://github.com/MavonEngine/Core/blob/main/plugins.json) im MavonEngine-Repository und wird bei jedem Aufruf vom `main`-Branch auf GitHub gelesen. Siehe [Offizielle Plugins](/de/werkzeuge/plugins#offizielle-plugins).

| Option | Standard | |
| --- | --- | --- |
| `--json` | | Die Liste als JSON ausgeben |
| `--url <url>` | `$MAVONENGINE_PLUGINS_URL` | Die Liste von woanders lesen, etwa von einem Fork oder einem Branch |

## `mavonengine install`

Installiert Pakete mit dem Paketmanager des Projekts. Für jedes Paket, das ein MavonEngine-[Plugin](/de/werkzeuge/plugins) ist, zeigt es an, wo das Plugin läuft und welche Prefabs es mitbringt, und fragt, ob es zu `mavonengine.json` hinzugefügt werden soll.

```bash
npx @mavonengine/cli install @mavonengine/http-monitoring

# Alles, was dein Paketmanager akzeptiert
npx @mavonengine/cli install @acme/forest@^2 file:../my-plugin --yes
```

| Option | Standard | |
| --- | --- | --- |
| `--cwd <dir>` | aktuelles Verzeichnis | Wo die Suche nach dem Projekt beginnt |
| `-y`, `--yes` | | Plugins ohne Nachfrage zu `mavonengine.json` hinzufügen |
| `--no-register` | | Nur installieren |

## `mavonengine make:plugin`

Erstellt ein [Plugin](/de/werkzeuge/plugins#ein-plugin-schreiben) im Projekt, in dem du bist, bereit zum Laden:

```bash
npx @mavonengine/cli make:plugin forest
npx @mavonengine/cli make:plugin @acme/forest --target server
```

Es schreibt `plugins/<name>/` (ohne den Scope). Das Verzeichnis enthält eine `package.json` mit dem `mavonengine`-Manifest, `src/client.ts` und/oder `src/server.ts` mit allen Hooks als Gerüst, eine `tsconfig.json` und eine README. Danach:

- fügt es `plugins/*` den `workspaces` in `package.json` hinzu (mit pnpm stattdessen eine `link:`-Abhängigkeit);
- trägt es das Plugin in `mavonengine.json` ein;
- führt es die Installation des Paketmanagers aus, die das Plugin nach `node_modules` verlinkt.

Das Manifest zeigt auf die TypeScript-Quellen, es gibt also keinen Build-Schritt. Vite kompiliert den Client-Einstiegspunkt, und Node 24 entfernt die Typen aus dem Server-Einstiegspunkt. Deshalb darf der Server-Einstiegspunkt nur Syntax verwenden, die Node entfernen kann (keine `enum`s oder Parameter-Properties), und er importiert seine eigenen Dateien mit `.ts`-Endung. Die erzeugte `tsconfig.json` erzwingt beides. Der Client lädt neu, wenn sich sein Einstiegspunkt ändert; starte den Spielserver nach Änderungen am Server-Einstiegspunkt neu. Um das Plugin später auf npm zu veröffentlichen, baue es wie die [offiziellen Plugins](https://github.com/MavonEngine/Core/tree/main/packages/plugins) nach `dist/` und lass das Manifest dorthin zeigen.

Es lehnt einen Namen ab, der schon in `mavonengine.json` steht oder installiert ist oder dessen Verzeichnis existiert, und überschreibt nie eine Datei.

| Option | Standard | |
| --- | --- | --- |
| `--target <side>` | `both` | `client`, `server` oder `both` |
| `--cwd <dir>` | aktuelles Verzeichnis | Wo die Suche nach dem Projekt beginnt |
| `--no-register` | | `mavonengine.json` nicht ändern |
| `--no-install` | | Den Paketmanager nicht zum Verlinken ausführen |

## `mavonengine asset:publish`

Kopiert die Dateien, die ein Plugin dich ändern lässt, in dein Projekt, etwa das [Layout des Mail-Plugins](/de/werkzeuge/mail#layout):

```bash
npx @mavonengine/cli asset:publish @mavonengine/mail
```

Sie landen in `resources/<package>/`, hier `resources/@mavonengine/mail/layout.html`. Das Plugin verwendet ab dann deine Kopie, ändere sie also dort und committe sie. Dateien, die du schon hast, bleiben erhalten, erneutes Veröffentlichen nach einem Update fügt also nur die neuen Dateien des Plugins hinzu. `--force` ersetzt deine durch die des Plugins.

Ein Plugin bietet Dateien mit `publish` in seinem Manifest an, siehe [Dateien zum Anpassen](/de/werkzeuge/plugins#dateien-zum-anpassen).

| Option | Standard | |
| --- | --- | --- |
| `--cwd <dir>` | aktuelles Verzeichnis | Wo die Suche nach dem Projekt beginnt |
| `--force` | | Deine Dateien durch die des Plugins ersetzen |

## `mavonengine build`

Führt das `build`-Skript des Projekts aus und listet dann auf, was jedes Plugin in das Release gelegt hat. Kopiert werden nur die geteilten Plugin-Assets und die der Prefabs, die in `mavonengine.json` aufgeführt sind — ein Release liefert oder lädt also nie eine Datei, die es nicht verwendet.

```bash
npx @mavonengine/cli build
```

## `mavonengine doctor`

Prüft das Projekt, in dem du bist, und sagt dir zu jedem gefundenen Problem, was zu tun ist. Es ändert nichts.

```bash
npx @mavonengine/cli doctor
```

```
MavonEngine project at ~/games/my-game (npm, @mavonengine/core 0.0.25)

Environment
  ✓ Node 24.4.0                 needs >=24
  ✓ @mavonengine/cli 0.0.6
  i @mavonengine/core 0.0.25    0.0.26 is out

mavonengine.json
  ✓ mavonengine.json  2 plugins
  ✗ appUrl "mygame.com"         is not an http(s) URL
      → e.g. "appUrl": "https://mygame.com"

Plugins
  ✓ @mavonengine/chat 0.0.3     core >=0.0.22
  ✗ @mavonengine/auth 0.2.0     made for @mavonengine/core >=0.0.26, the project has 0.0.25
      → mavonengine install @mavonengine/auth@0.1.1

2 errors, 0 warnings
```

- **Environment**: die Node-Version, verglichen mit dem, was die CLI und das installierte `@mavonengine/core` brauchen. Dann für jedes `@mavonengine/*`-Paket in `package.json`: ob es installiert ist und zum dortigen Bereich passt (oder ein `npm install` fällig ist) und ob eine neuere Version erschienen ist.
- **mavonengine.json**: ob die Datei lesbar ist, eine `appUrl`, die keine http(s)-URL ist, ein `database`, `auth` oder `notifications`, das ein Plugin nennt, das nicht in `plugins` steht oder ausgeschaltet ist, Einträge in falscher Form und Einstellungen, die es nicht kennt (Tippfehler).
- **Migrations**: die [`upgrade`](#mavonengine-upgrade)-Migrationen im Core des Projekts, die das Projekt noch nicht hatte.
- **Plugins**: Jedes Plugin in `mavonengine.json` muss installiert, ein MavonEngine-Plugin und gebaut sein (seine Einstiegspunkte existieren). Die Assets der verwendeten Prefabs müssen vorhanden sein, und das Plugin muss für den Core des Projekts gemacht sein. Der unterstützte Core eines Plugins ist `engine` in seinem [Manifest](/de/werkzeuge/plugins#ein-plugin-schreiben), sonst seine `@mavonengine/core`-Peer-Abhängigkeit. Passt ein Plugin nicht, durchsucht doctor die auf npm veröffentlichten Versionen und nennt die neueste, die passt. Es weist auch auf Plugins hin, die installiert sind, aber nicht in `mavonengine.json` stehen.

Auch der Spielserver und das Vite-Plugin prüfen `engine`, wenn sie Plugins laden. Ein Plugin für einen anderen Core wird trotzdem geladen, mit einer Warnung, die auf `mavonengine doctor` verweist.

Versionsabfragen gehen an die npm-Registry (`npm_config_registry`, wenn gesetzt, sonst registry.npmjs.org) und senden ihr die Namen der `@mavonengine/*`-Pakete und Plugins des Projekts. `--offline` lässt sie weg. Ist die Registry nicht erreichbar, gibt doctor eine Warnung aus und prüft den Rest trotzdem.

Der Exit-Code ist 1, wenn etwas nicht stimmt (✗), sonst 0. Mit `--strict` schlagen auch Warnungen (!) fehl; Hinweise (i) nie. `--json` gibt die Ergebnisse für CI und Skripte aus.

| Option | Standard | |
| --- | --- | --- |
| `--offline` | | Die npm-Registry nicht fragen |
| `--strict` | | Auch bei Warnungen fehlschlagen |
| `--json` | | Die Ergebnisse als JSON ausgeben |
| `--cwd <dir>` | aktuelles Verzeichnis | Wo die Suche nach dem Projekt beginnt |

## `mavonengine upgrade`

Hebt das Projekt auf das neueste `@mavonengine/core`, mit Plugins, die damit funktionieren, und nimmt dann die Änderungen an den Projektdateien vor, die der neue Core braucht.

```bash
npx @mavonengine/cli upgrade --dry-run   # sehen, was passieren würde
npx @mavonengine/cli upgrade
```

1. **Pakete.** `@mavonengine/core` geht auf seine neueste Version in der npm-Registry oder auf `--to <version>`. Jedes Plugin geht auf seine neueste Version, deren `engine`-Bereich diesen Core annimmt. Die anderen `@mavonengine/*`-Pakete gehen auf ihre neueste Version, deren `@mavonengine/core`-Peer-Bereich ihn annimmt. Nichts wird herabgestuft, und Pakete aus `file:`, git oder einer anderen Quelle bleiben unverändert. Hat ein Plugin keine Version für den neuen Core, bricht das Upgrade ab, bevor etwas installiert wird; wähle mit `--to` einen älteren Core, entferne das Plugin oder übergib `--force`. Der Paketmanager des Projekts installiert die Pakete. Jedes bleibt in `dependencies` oder `devDependencies`, und fest gepinnte Versionen bleiben gepinnt.
2. **Migrationen.** Sie kommen aus dem neu installierten Core, der neue Core entscheidet also, was migriert wird. Jede wird als Diff gezeigt, bevor etwas geschrieben wird. Angewendete Migrationen werden unter `migrations` in `mavonengine.json` vermerkt und nie wieder angeboten, auch wenn du eine absichtlich rückgängig machst. Fügt eine Migration eine Abhängigkeit hinzu, installiert der Paketmanager sie.
3. **Doctor.** [`mavonengine doctor`](#mavonengine-doctor) prüft das Ergebnis, und der Exit-Code ist der von doctor.

| Migration | Was sie ändert |
| --- | --- |
| `0.0.22-dev-script` | `npm run dev` startet `mavonengine dev`. Das alte `dev`-Skript wird zu `dev:server`, und `@mavonengine/cli` wird eine Dev-Abhängigkeit |
| `0.0.25-app-name-title` | Der `<title>` der `index.html` wird zu `%MAVONENGINE_APP_NAME%`. Der alte Titel wird zu `appName` in `mavonengine.json`, der Browser-Tab zeigt also weiter denselben Namen |

Das Upgrade fragt vor dem Installieren und vor dem Schreiben. `--yes` überspringt beide Fragen und ist ohne Terminal erforderlich. Es startet nicht mit nicht committeten Änderungen in git, damit du seine Änderungen für sich prüfen und rückgängig machen kannst; `--allow-dirty` setzt das außer Kraft. Hast du die Pakete selbst installiert, führt `--only-migrations` nur die Schritte 2 und 3 aus.

| Option | Standard | |
| --- | --- | --- |
| `--to <version>` | neueste | Die `@mavonengine/core`-Version, auf die gehoben wird |
| `--only-migrations` | | Die Pakete nicht anfassen |
| `--dry-run` | | Zeigen, was passieren würde, nichts ändern |
| `-y`, `--yes` | | Nicht fragen |
| `--force` | | Auch upgraden, wenn ein Plugin keine Version für den neuen Core hat |
| `--allow-dirty` | | Mit nicht committeten Änderungen starten |
| `--cwd <dir>` | aktuelles Verzeichnis | Wo die Suche nach dem Projekt beginnt |

## `mavonengine dashboard`

Ein Live-Terminal-Dashboard für einen laufenden Spielserver, siehe [Monitoring](/de/werkzeuge/monitoring). Mit einem [Datenbank-Plugin](/de/werkzeuge/datenbank) bekommt es einen Database-Tab; übergib das Admin-Token des Servers als `--token`, um ihn auf einem Server zu lesen, der eines hat.

```bash
npx @mavonengine/cli dashboard
npx @mavonengine/cli dashboard --sim   # simulierte Daten, kein Server nötig
```

## `mavonengine mcp`

Ein Model-Context-Protocol-Server für KI-Assistenten, siehe [KI-Assistenten](/de/werkzeuge/ki-assistenten).
