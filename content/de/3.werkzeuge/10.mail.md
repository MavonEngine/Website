`@mavonengine/mail` sendet Mails vom Spielserver: Willkommensmails, Passwort-Resets, Quittungen. Mails kommen auf die [Job-Warteschlange](/de/werkzeuge/warteschlange) des Servers und werden erneut versucht, wenn der Mailserver nicht erreichbar ist, sodass ein langsamer oder fehlerhafter Anbieter das Spiel nie aufhält.

```bash
npx @mavonengine/cli install @mavonengine/mail
```

Bis du einen [Transport](#transporte) einrichtest, werden Mails ins Log des Servers geschrieben statt gesendet, du kannst Mails in der Entwicklung also ohne Konto irgendwo bauen und testen. Mit installiertem MailDev landen sie stattdessen im [Dev-Posteingang](#dev-posteingang) des Admin-Panels, wo du jede Mail in ihrem Layout ansehen kannst.

Damit bestätigt [`@mavonengine/auth`](/de/werkzeuge/auth#e-mail) E-Mail-Adressen und setzt vergessene Passwörter zurück, und [`@mavonengine/notifications`](/de/werkzeuge/benachrichtigungen#mail) verschickt Benachrichtigungen per Mail.

## Mails senden

Schreib eine Mail als Klasse, die `Mailable` erweitert:

```typescript
import { escapeHtml, Mailable } from '@mavonengine/mail'

export class Welcome extends Mailable {
  constructor(private name: string) {
    super()
  }

  subject() {
    return `Welcome, ${this.name}!`
  }

  // Die Zeile, die Postfächer neben dem Betreff zeigen
  preheader() {
    return 'Your account is ready'
  }

  text() {
    return `Good to have you, ${this.name}.`
  }

  html() {
    // Was Spieler geschrieben haben, escapen, bevor es ins HTML kommt
    return `<p>Good to have you, <b>${escapeHtml(this.name)}</b>.</p>`
  }
}
```

In einem Plugin ist das Mail-Plugin [`ctx.plugin('@mavonengine/mail')`](/de/werkzeuge/plugins#andere-plugins-verwenden). Es ist undefined, wenn das Projekt es nicht hat, ein Plugin kann Mails also optional machen:

```typescript
export default defineServerPlugin({
  http(app, ctx) {
    app.post('/api/shop/buy', async (req, res) => {
      const order = await buy(req.body)
      await ctx.plugin('@mavonengine/mail')?.to(order.email).send(new Receipt(order))
      res.json(order)
    })
  },
})
```

Im Server-Code des Spiels verwendest du `mail(server)`:

```typescript
import { mail } from '@mavonengine/mail'

await mail(server)?.to('Ada <ada@example.com>').cc('team@example.com').send(new Welcome('Ada'))
```

- **Standardmäßig eingereiht:** `send()` erfüllt sich, sobald die Mail auf der Warteschlange liegt, mit `{ queued: true, jobId }`. Die Warteschlange versucht sie 3 Mal, mit 10 Sekunden und dann einer Minute Pause, und bewahrt sie als `mail:send` unter den [fehlgeschlagenen Jobs](/de/werkzeuge/warteschlange#fehlgeschlagene-jobs) auf, wenn jeder Versuch scheiterte. Mit einem Datenbank-Plugin überstehen eingereihte Mails einen Neustart.
- **Sofort:** `sendNow()` sendet im Aufruf und lehnt ab, wenn der Transport ablehnt. Ebenso ein Mailable mit `queued = false` und `send(mailable, { queued: false })`. `send(mailable, { delayMs })` sendet sie später.
- **Beim Senden geprüft:** Eine Mail ohne Empfänger, ohne Betreff oder ohne Text oder HTML, mit einer Adresse, die keine ist, oder mit einem Zeilenumbruch im Betreff, einem Namen oder einem Header lässt `send()` einen `MailError` werfen. Du erfährst es sofort, nicht erst im Log, wenn die Warteschlange dazu kommt.
- **Beim Senden gerendert:** Auf der Warteschlange wartet die fertige Mail als reines JSON, nicht die Klasse.
- **Ausgeschrieben:** `send({ to, subject, text, html })` sendet eine Mail ohne Klasse.

`from`, `replyTo` und `headers()` lassen sich pro Mailable setzen. Eine Mail ohne `from` bekommt das aus den Optionen.

## Layout

HTML-Mails werden in einem Layout gesendet: der Name des Spiels oben, die Mail auf einer weißen Karte, darunter eine Fußzeile. Eine Mail nur mit Text bekommt daraus HTML, einen Absatz pro Leerzeile, sodass jede Mail gleich aussieht. Schreib `html()` als das, was ins Layout kommt, nicht als ganze Seite.

Um das Layout zu ändern, veröffentliche es mit [`asset:publish`](/de/werkzeuge/cli#mavonengine-assetpublish) ins Projekt:

```bash
npx @mavonengine/cli asset:publish @mavonengine/mail
```

Das kopiert es nach `resources/@mavonengine/mail/layout.html`, das ab dann verwendet wird. Außerhalb der Produktion wird die Datei für jede Mail neu gelesen, eine Änderung zeigt sich also ohne Neustart in der nächsten.

`{{ name }}` wird escaped eingesetzt, `{{{ name }}}` unverändert:

| | |
| --- | --- |
| `{{{ content }}}` | Das HTML der Mail, oder ihr Text als Absätze |
| `{{ subject }}` | Der Betreff |
| `{{ preheader }}` | Aus `preheader()` des Mailables, oder `preheader` in `send()` |
| `{{ appName }}` | Der Name des Spiels, [`appName`](/de/werkzeuge/plugins#mavonenginejson) in `mavonengine.json`, sonst der Name des Absenders |
| `{{ appUrl }}` | Wo das Spiel ist, [`appUrl`](/de/werkzeuge/plugins#mavonenginejson) in `mavonengine.json` oder `MAVONENGINE_APP_URL`. Leer, wenn nicht gesetzt |
| `{{ year }}` | Das aktuelle Jahr |
| alles andere | Aus der Option `layoutData`, z. B. `{{ footer }}` |

Kommentare werden aus der Mail entfernt, außer den bedingten Kommentaren von Outlook (`<!--[if mso]>`). Mail-Clients ignorieren das meiste CSS und `<style>`-Blöcke, bleib also bei Tabellen und Inline-Styles, wie das Standard-Layout.

Ein Mailable mit `layout = false`, oder `send({ …, layout: false })`, wird ohne Layout gesendet; die Option `layout` schaltet es für alle Mails ab. Lässt sich das Layout nicht lesen, gehen Mails ohne es hinaus, und das Log sagt es.

## Transporte

Mails gehen jeweils über einen Transport.

### SMTP

Fast jeder Anbieter hat ein SMTP-Relay: Mailgun, Amazon SES, Postmark, SendGrid, Resend oder dein eigener Server. Leg den Server in die Optionen und das Passwort in die Umgebung:

```json
{
  "plugins": {
    "@mavonengine/mail": {
      "options": {
        "from": "My Game <noreply@mygame.com>",
        "smtp": { "host": "smtp.mailgun.org", "port": 587, "user": "postmaster@mg.mygame.com" }
      }
    }
  }
}
```

```bash
MAVONENGINE_MAIL_SMTP_PASSWORD=… npm start
```

Oder alles in eine URL: `MAVONENGINE_MAIL_SMTP_URL=smtps://user:password@smtp.example.com`. Port 465 verbindet mit TLS; andere Ports wechseln mit STARTTLS, wenn der Server es anbietet.

### nodemailer-Transporte

Mails werden mit [nodemailer](https://nodemailer.com) gesendet, also funktionieren auch seine Transporte. Das sind Objekte statt JSON, richte sie daher im Code ein:

```typescript
import { SendEmailCommand, SESv2Client } from '@aws-sdk/client-sesv2'
import { mail } from '@mavonengine/mail'

mail(server)?.useNodemailer({ SES: { sesClient: new SESv2Client({ region: 'eu-west-1' }), SendEmailCommand } }, 'ses')
```

Community-Transporte wie `nodemailer-mailgun-transport` funktionieren genauso.

### Eigene

Ein Transport ist ein Objekt mit einem `name` und einem `send()`, das sich erfüllt, sobald die Mail übergeben wurde. Mehr braucht das Plugin eines Anbieters nicht:

```typescript
import type { MailTransport } from '@mavonengine/mail'
import { formatAddress } from '@mavonengine/mail'

const postmark: MailTransport = {
  name: 'postmark',
  async send(message) {
    const res = await fetch('https://api.postmarkapp.com/email', {
      method: 'POST',
      headers: { 'X-Postmark-Server-Token': token, 'Content-Type': 'application/json' },
      body: JSON.stringify({ From: formatAddress(message.from!), To: message.to.map(formatAddress).join(', '), Subject: message.subject, TextBody: message.text, HtmlBody: message.html }),
    })
    if (!res.ok)
      throw new Error(`Postmark answered ${res.status}`)
    return { messageId: (await res.json()).MessageID }
  },
}

ctx.plugin('@mavonengine/mail')?.useTransport(postmark)
```

`send()` sollte ablehnen, wenn die Mail nicht angenommen wurde, damit die Warteschlange es erneut versucht. Ein `close()`, falls der Transport eines hat, wird aufgerufen, wenn er ersetzt wird und wenn der Server stoppt.

### In Tests

`memoryTransport()` behält Mails in seinem Array `sent`, statt sie zu senden:

```typescript
import { mail, memoryTransport } from '@mavonengine/mail'

const memory = memoryTransport()
mail(server)!.useTransport(memory)
// …
expect(memory.sent[0].subject).toBe('Welcome, Ada!')
```

## Dev-Posteingang

In der Entwicklung können die Mails des Spiels in einem [MailDev](https://maildev.github.io/maildev/)-Posteingang im [Admin-Panel](/de/werkzeuge/admin-panel) des Spielservers landen, statt nur im Log. Installiere MailDev als Dev-Abhängigkeit:

```bash
npm i -D maildev
```

Öffne dann `http://localhost:8050/admin/mail/`. Jede Mail, die das Spiel sendet, erscheint dort, sobald sie ankommt, mit HTML, Text, Headern und Quelltext. Nichts verlässt deinen Rechner, und die Mail braucht keinen Absender. Die Mails liegen in `.mavonengine/maildev` und sind nach einem Neustart des Dev-Servers noch da.

::div{class="rounded-xl overflow-hidden shadow-2xl my-6"}
![Der Dev-Posteingang im Admin-Panel: die Mails, die das Spiel gesendet hat, mit einer Level-up-Mail in ihrem Layout geöffnet](/static/plugin-mail.png)
::

- MailDev läuft im Spielserver, mit seinem SMTP- und Webserver auf freien Ports, die nur dieser Rechner erreicht.
- Seine Oberfläche wird unter `/admin/mail/inbox/` ausgeliefert, hinter der Anmeldung des Admin-Panels, in einem dunklen Theme wie das Panel.
- Seine Live-Updates nutzen HTTP-Polling statt eines WebSockets, der an der Anmeldung vorbeigehen würde.

Der Dev-Posteingang wird nur verwendet, solange kein SMTP-Server und kein Transport eingerichtet ist, und nur in der Entwicklung: nie mit `NODE_ENV=production` oder in Tests. Ohne installiertes `maildev` werden Mails wie bisher ins Log geschrieben. Schalte ihn mit `"devInbox": false` aus.

## Optionen

Setze sie unter dem Plugin in `mavonengine.json`. Alle sind optional.

| Option | Standard | |
| --- | --- | --- |
| `from` | | Der Absender von Mails, die keinen nennen, etwa `My Game <noreply@mygame.com>`. Für jeden Transport außer dem Log nötig |
| `smtp` | | Der SMTP-Server: `{ host, port, secure, user }`, oder eine URL ohne Passwort. Siehe [SMTP](#smtp) |
| `queued` | `true` | Mails einreihen oder im Aufruf senden. `queued` eines Mailables und die Optionen von `send()` gehen vor |
| `queue` | `default` | Die Warteschlange für Mails. Gib Mails mit `queue.queues` des Servers eine eigene [Warteschlange](/de/werkzeuge/warteschlange#optionen), damit sie nicht hinter anderen Jobs warten |
| `tries` | `3` | Wie oft eine eingereihte Mail versucht wird, bevor sie als fehlgeschlagen gilt |
| `backoffMs` | `[10000, 60000]` | Wie lange vor einem erneuten Versuch gewartet wird, in ms: eine Zahl, oder eine pro Versuch, wobei sich die letzte wiederholt |
| `layout` | `true` | Mails im [Layout](#layout) senden |
| `layoutData` | `{}` | Weitere Werte für das Layout, z. B. `{ "footer": "You get this because you play My Game." }` |
| `devInbox` | `true` | In der Entwicklung Mails in den [Dev-Posteingang](#dev-posteingang) senden, solange kein Transport eingerichtet ist |

| Umgebung | |
| --- | --- |
| `MAVONENGINE_MAIL_FROM` | Überschreibt `from` |
| `MAVONENGINE_MAIL_SMTP_URL` | Der SMTP-Server mit Zugangsdaten, überschreibt `smtp` |
| `MAVONENGINE_MAIL_SMTP_PASSWORD` | Das Passwort für `smtp`. Halte es aus `mavonengine.json` heraus |

Anhänge gibt es noch nicht.
