`mavonengine mcp` ist ein [Model Context Protocol](https://modelcontextprotocol.io)-Server über stdio. Er lässt einen KI-Coding-Assistenten auf dein laufendes Spiel schauen — den Spielserver und die im Browser geöffneten Spiel-Tabs — und diese Dokumentation lesen. Er funktioniert mit jedem MCP-Client und jedem Modell: Claude Code, Cursor, VS Code, Codex, Gemini CLI, Zed oder einem lokalen Modell.

Alle Tools sind schreibgeschützt.

## Setup

Projekte, die mit `mavonengine create` erstellt wurden, enthalten eine `.mcp.json`, sodass Clients, die sie lesen (wie Claude Code), den Server automatisch erkennen. Für andere Clients registrierst du ihn als stdio-Server:

```json
{
  "mcpServers": {
    "mavonengine": { "command": "npx", "args": ["-y", "@mavonengine/cli", "mcp"] }
  }
}
```

Er nimmt `--host`, `--port`, `--url` (die Basis-URL des Servers, z.B. `http://localhost:8050`) und `--token` (das Metrik- oder das [Admin-Token](/de/netzwerk/server#admin-token)) wie das [Dashboard](/de/werkzeuge/monitoring). Wenn Vite den Client auf einem eigenen Port ausliefert, übergib `--client-url`, z.B. `http://localhost:5173`.

## Tools für den Spielserver

| Tool | |
| --- | --- |
| `server_status` | Uptime, Tick-Zeit im Verhältnis zum Budget, CPU, Bandbreite, Speicher, Anzahl von Spielern / Entities / Physikobjekten |
| `server_metrics` | Der vollständige Metrik-Snapshot, optional mit Verlauf pro Sekunde |
| `list_players` | Verbundene Spieler mit Position und Verbindungsdetails |
| `get_scene` | Die aktive Szene: Datei, Hot Reload, ungespeicherte Änderungen, Einstellungen und Objekte (nur Dev) |
| `list_entities` | Entities in der Welt, gefiltert nach Typ und Distanz zu einem Punkt (nur Dev) |
| `get_entity` | Eine Entity mit dem Zustand, den sie an Clients sendet (nur Dev) |
| `recent_logs` | Server-Logzeilen, gefiltert nach Level und Text |
| `recent_requests` | HTTP-Anfragen, die der Server beantwortet hat, gefiltert nach Pfad und Status |
| `network_packets` / `network_packet` | Pakete, die der Server gesendet und empfangen hat, und seine Netzwerk-Events, pro Client: Größe, Tick, Eingabe-Sequenz-ID; sowie ein einzelnes Paket mit Payload (nur Dev) |
| `network_sync` | Wer bekommt was gesendet: die verfolgten Entities und das letzte Zustandsupdate jedes Spielers, und von wie vielen Spielern jede Entity verfolgt wird (nur Dev) |

Die Szenen-, Entity- und Netzwerk-Tools lesen `GET /api/game/dev/*`, das nur existiert, wenn `NODE_ENV` nicht `production` ist.

## Client-Tools

Für die Spiel-Tabs, die geöffnet sind, während Vite den Client im Dev-Modus ausliefert:

| Tool | |
| --- | --- |
| `list_clients` | Offene Tabs: Seite, Editor oder Spieler, die ID des Spielers auf dem Server, Sichtbarkeit, FPS |
| `client_status` | Draw Calls und Dreiecke, GPU-Geometrien / -Texturen / -Programme, JS-Heap, Canvas, Kamera |
| `client_entities` / `client_entity` | Die Welt des Tabs, in derselben Form wie die des Servers, mit markiertem lokalen Spieler |
| `client_scene` | Die im Tab geladene Szene und welche Objekte der Client gebaut hat |
| `client_network` | Verbindung, Ping, Eingaben, die der Server noch nicht bestätigt hat, und das letzte Zustandsupdate: sein Server-Tick, Ack und Alter |
| `client_packets` / `client_packet` | Pakete, die der Tab gesendet und empfangen hat, und seine Netzwerk-Events, sowie ein einzelnes Paket mit Payload |
| `network_timeline` | Die Aufzeichnungen des Servers zu einem Tab und die des Tabs selbst, nach Zeit zusammengeführt |
| `client_logs` | Konsolenausgabe, nicht abgefangene Fehler und unbehandelte Rejections |
| `client_screenshot` | Was der Tab rendert, als Bild (das WebGL-Canvas, ohne HTML-UI) |
| `client_trace` | Zeichnet ein paar Sekunden auf und analysiert Frame-Zeiten, CPU vs. GPU, Composer-Passes, Ticks, WebGL-Arbeit, den Flaschenhals und die schlimmsten Ruckler. Speichert eine Trace-Datei für Perfetto, `chrome://tracing` oder speedscope |
| `compare_entity` | Eine Entity auf dem Server neben der Kopie eines Tabs: Abweichungen bei Position / Rotation / Skalierung und unterschiedliche Felder |

Client-Tools nehmen eine `clientId` aus `list_clients`; ohne sie fragen sie den einzigen offenen Tab, oder den einzigen, der nicht den Editor ausführt.

Sie laufen über die Dev-Bridge des Vite-Plugins in `@mavonengine/core/vite.config`. Diese wird nur im Dev-Modus hinzugefügt, nie in Builds; schalte sie mit `mavonEnginePlugins({ devBridge: false })` ab.

Damit `compare_entity` deinen eigenen Spieler dem des Servers zuordnen kann, setz `game.localPlayer` auf die Entity, die der Tab steuert: Der Server ordnet Spieler nach Socket-ID zu, die der Client oft nicht kennt.

Die Netzwerk-Tools lesen, was beide Seiten während der Entwicklung aufzeichnen, siehe [Netzwerk-Debugging](/de/netzwerk/zustandssync#netzwerk-debugging). `network_timeline` ordnet die beiden Seiten nach ihren eigenen Uhren, die auf einem Rechner übereinstimmen.

## Plugin-Tools

| Tool | |
| --- | --- |
| `list_plugins` | Die Plugins in der `mavonengine.json` des Projekts: Version, ob jedes aktiviert ist und auf dem Server läuft, seine Prefabs und die von ihm registrierten HTTP-Endpunkte |
| `available_plugins` | Die [offiziellen Plugins](/de/werkzeuge/plugins#offizielle-plugins): was jedes tut, wo es läuft, der Befehl, der es installiert, und ob das Projekt es bereits hat |
| `plugin_readme` | Die README eines davon als Markdown: seine Optionen, wie sich ein Spiel einklinkt und seine Grenzen |

Damit kann ein Assistent ein Plugin vorschlagen, statt nachzubauen, was eines bereits kann, und es anhand der Readme einrichten. Installieren kann er keines: Alle Tools sind schreibgeschützt, er gibt dir also den Befehl. `available_plugins` und `plugin_readme` lesen bei Verwendung von GitHub; `--plugins-url` oder `MAVONENGINE_PLUGINS_URL` richtet sie auf eine andere Liste, `--no-plugin-list` lässt sie weg.

## Dokumentations-Tools

| Tool | |
| --- | --- |
| `docs_list_pages` | Jede Doku-Seite mit Pfad, Titel, Beschreibung und Kategorie |
| `docs_get_page` | Eine Doku-Seite als Markdown, nach Pfad (z.B. `/networking/state-sync`) |

Sie werden an den MCP-Server von mavonengine.com (`https://mavonengine.com/mcp`) durchgereicht, sodass die Antworten aus der aktuellen Doku kommen. `--docs-url` richtet sie auf einen anderen Doku-Server, `--no-docs` lässt sie weg.
