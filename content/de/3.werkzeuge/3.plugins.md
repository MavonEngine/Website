Ein Engine-Plugin ist ein npm-Paket, das dem Client, dem Spielserver oder beiden Code hinzufügt und Prefabs und Assets mitbringen kann. Installiere eines mit der [CLI](/de/werkzeuge/cli):

```bash
npx @mavonengine/cli install my-custom-plugin
```

## Offizielle Plugins

Die offiziellen Plugins stehen in [`plugins.json`](https://github.com/MavonEngine/Core/blob/main/plugins.json) im Root des MavonEngine-Repositorys:

| Plugin | Läuft auf | |
| --- | --- | --- |
| [`@mavonengine/http-monitoring`](/de/werkzeuge/monitoring#browser-dashboard) | Server | Das Spielserver-Dashboard im Browser |
| [`@mavonengine/chat`](/de/werkzeuge/chat) | Client und Server | Text-Chat im Spiel mit Rate-Limit, Stummschaltungen, Umgebungs-Chat und einer Admin-API |
| [`@mavonengine/sqlite`](/de/werkzeuge/datenbank) | Server | Eine SQLite-Datenbank für den Spielserver und seine Plugins, auf dem in Node eingebauten `node:sqlite` |
| [`@mavonengine/auth`](/de/werkzeuge/auth) | Client und Server | Spieler-Accounts mit Anmeldungen und Sitzungen, damit der Spielserver weiß, wer sich verbindet |
| [`@mavonengine/mail`](/de/werkzeuge/mail) | Server | Mails vom Spielserver, eingereiht und wiederholt, über SMTP oder jeden nodemailer-Transport |
| [`@mavonengine/notifications`](/de/werkzeuge/benachrichtigungen) | Client und Server | Spieler im Spiel, per Mail und zum späteren Lesen benachrichtigen: `player.notify(new LevelUp())` |

`mavonengine plugins` gibt die Liste aus und liest sie jedes Mal von GitHub, ein neues Plugin erscheint also, sobald es hinzugefügt wurde. Dieselbe Liste, mit dem, was dein Projekt noch nicht hat, erscheint in:

- dem **Plugins**-Tab des [Dashboards](/de/werkzeuge/monitoring#terminal-dashboard), wo `i` unter `mavonengine dev` das ausgewählte Plugin installiert;
- der **Plugins**-Ansicht des [Editors](/de/kernkonzepte/level-editor#server-und-plugins), die auch die Readme jedes Plugins zeigt und beliebige andere Pakete installiert;
- dem Tool `available_plugins` des [MCP-Servers](/de/werkzeuge/ki-assistenten#plugin-tools), damit ein Assistent ein Plugin vorschlagen kann, statt nachzubauen, was eines bereits kann.

Die Installation aus dem Dashboard oder dem Editor fragt vorher nach, da der Code eines Pakets auf deinem Rechner läuft, fügt das Plugin dann zu `mavonengine.json` hinzu und startet die Dev-Server neu.

Um ein eigenes Plugin aufzulisten, füge einen Eintrag zu `plugins.json` hinzu: `package` (der npm-Name) ist erforderlich; `name`, `description`, `target`, `engine` (der unterstützte `@mavonengine/core`-Bereich), `homepage` und `readme` (die URL seiner README als Markdown) sind optional.

## mavonengine.json

Aktivierte Plugins stehen in `mavonengine.json` im Projekt-Root, neben `package.json`:

```json
{
  "appUrl": "https://mygame.com",
  "appName": "My Game",
  "plugins": {
    "my-custom-plugin": { "enabled": true, "prefabs": ["Tree"], "options": { "density": 2 } }
  }
}
```

| Feld | Beschreibung |
|-------|-------------|
| `enabled` | `false` schaltet das Plugin ab, ohne es zu deinstallieren |
| `prefabs` | Die Plugin-Prefabs, die das Projekt verwendet. Der Editor fügt ein Prefab hinzu, wenn du es platzierst. Nur die Assets dieser Prefabs (plus die geteilten) kommen ins Release |
| `options` | Wird dem Plugin als `ctx.options` übergeben |

Neben `plugins` steht in der Datei, was für das ganze Projekt gilt. Alles davon ist optional:

| Schlüssel | |
| --- | --- |
| `appUrl` | Wo das Spiel ist, etwa `https://mygame.com`. Links, die aus dem Spiel hinausführen, etwa in [Mails](/de/werkzeuge/mail), zeigen dorthin. `MAVONENGINE_APP_URL` überschreibt es, zum Beispiel pro Deployment. Ein Produktionsserver baut solche Links nie aus der Adresse, die eine Anfrage nennt, setz es also vor dem Deployment |
| `appName` | Der Name des Spiels, in Mails und im Browser-Tab: `%MAVONENGINE_APP_NAME%` in der `index.html` des Clients wird dazu, im Dev-Modus und im Build (`MavonEngine` ohne einen). `mavonengine create` setzt ihn aus dem Projektnamen. Baue den Client nach einer Änderung neu |
| `database` | Das zu verwendende [Datenbank-Plugin](/de/werkzeuge/datenbank), wenn mehr als eines aktiviert ist |
| `auth` | Das zu verwendende [Auth-Plugin](#spieler-authentifizieren), wenn mehr als eines aktiviert ist |
| `notifications` | Das [Benachrichtigungs-Plugin](/de/werkzeuge/benachrichtigungen), über das `notify()` sendet, wenn mehr als eines aktiviert ist |

Ohne `database`, `auth` oder `notifications` wird das erste aktivierte Plugin dieser Art verwendet. Server-Plugins bekommen `appUrl` und `appName` als `ctx.appUrl` und `ctx.appName`; die Optionen `appUrl` und `appName` des Servers gehen der Datei vor.

Der Client lädt neu, wenn sich die Plugins ändern. Starte den Spielserver neu, um ein neues Server-Plugin zu laden.

## Ein Projekt einrichten

Projekte, die mit `mavonengine create` erstellt wurden, sind bereits eingerichtet. Für ein bestehendes Projekt:

```typescript
// Client: vor new Game()
import Game from '@mavonengine/core/Game'
import plugins from 'virtual:mavonengine/plugins'

Game.usePlugins(plugins)
```

```typescript
// Server: das Verzeichnis mit mavonengine.json
const server = new MyServer(logger, physicsWorld, { plugins: { root: projectRoot } })
await server.start()
```

Die Vite-Konfiguration des Clients muss `@mavonengine/core/vite.config` erweitern. Diese stellt `virtual:mavonengine/plugins` bereit, liefert Plugin-Assets im Dev-Modus aus und kopiert sie ins Release.

## Ein Plugin schreiben

Füge der `package.json` des Plugins ein `mavonengine`-Feld hinzu:

```json
{
  "name": "my-custom-plugin",
  "type": "module",
  "mavonengine": {
    "target": "both",
    "client": "./dist/client.js",
    "server": "./dist/server.js",
    "engine": "^0.0.25",
    "publish": "./publish",
    "assets": {
      "dir": "./assets",
      "shared": ["textures/bark.png"],
      "prefabs": {
        "Tree": ["models/tree.glb"],
        "Rock": ["models/rock.glb"]
      }
    }
  }
}
```

- `target`: `client`, `server` oder `both`. Die passenden Einträge sind erforderlich.
- `assets`: Pfade relativ zu `dir` (Standard `assets`), ausgeliefert unter `/plugins/<package>/<path>`. Im Dev-Modus alle; in einem Release nur die geteilten und die der verwendeten Prefabs.
- `publish`: ein Verzeichnis mit Dateien, die das Projekt ändern darf, etwa ein Mail-Layout, siehe [Dateien zum Anpassen](#dateien-zum-anpassen).

Jeder Einstiegspunkt exportiert das Plugin als Default-Export. Jeder Hook bekommt als letztes Argument den Kontext des Plugins, mit `package`, `options`, `game` und `logger`.

### Client

```typescript
import { defineClientPlugin } from '@mavonengine/core/Plugins/types'

export default defineClientPlugin({
  assets: ctx => [{ name: 'tree', type: 'gltfModel', path: ctx.assetUrl('models/tree.glb') }],
  setup(ctx) {
    ctx.registerPrefab({
      name: 'Tree',
      spawn: position => ({ object: new Tree(position) }),
    })
  },
  update(delta, ctx) {},
  // Nur im Dev-Modus, wenn der Editor startet
  editor(ctx) {
    ctx.editor.on('objectSelected', () => {})
  },
})
```

Der Client-Kontext hat außerdem `plugin()`, um [andere Plugins zu verwenden](#andere-plugins-verwenden), und `registerSceneObject()`, um [Szenenobjekt-Typen](/de/kernkonzepte/szenen#szenenobjekt-typen) hinzuzufügen. Ein Client-Plugin kann auch das Token liefern, mit dem sich das Spiel verbindet, siehe [Spieler authentifizieren](#spieler-authentifizieren).

### Server

```typescript
import { defineServerPlugin } from '@mavonengine/core/Plugins/types'

export default defineServerPlugin({
  setup(ctx) {},
  // Läuft nach den eigenen onHttp-Routen des Servers, vor dem Spiel-Client
  http(app, ctx) {
    app.get('/api/my-plugin/status', (_req, res) => res.json({ ok: true }))
  },
  onConnection(channel, client, ctx) {},
  onDisconnect(channel, ctx) {},
  tick(delta, ctx) {},
  // Darf ein Promise zurückgeben: Die Datenbank wird geschlossen, sobald es erfüllt ist
  destroy(ctx) {},
})
```

Der Server-Kontext hat außerdem `server`, `projectRoot`, `appUrl`, `appName`, `registerSceneObject()`, `requireAdmin`, `adminToken`, `db`, `table()`, `queue`, `identity()`, `plugin()` und `publishedFile()`. `ctx.queue` ist die [Job-Warteschlange](/de/werkzeuge/warteschlange) des Servers: Registriere die Job-Klassen des Plugins in `setup()`. Plugins erreichen die Physikwelt über `ctx.game.physicsWorld`, siehe [Physik](/de/kernkonzepte/physik).

Die Routen, die ein Plugin registriert, werden mit seinem Namen in den Tabs Routes und Plugins des Dashboards aufgeführt. Beschreibe mit [`describeRoute()`](/de/netzwerk/server#routen-beschreiben), was sie tun.

### Andere Plugins verwenden

Ein Plugin bietet anderen Plugins etwas mit `api()` an, und sie bekommen es mit `ctx.plugin('<package>')`. Das ist undefined, wenn dieses Plugin nicht installiert, aktiviert oder gestartet ist oder keine API hat, ein Plugin kommt also ohne die aus, die es verwenden kann:

```typescript
// @acme/shop: mailt eine Quittung, wenn das Projekt das Mail-Plugin hat
export default defineServerPlugin({
  http(app, ctx) {
    app.post('/api/shop/buy', async (req, res) => {
      const order = await buy(req.body)
      await ctx.plugin('@mavonengine/mail')?.to(order.email).send(new Receipt(order))
      res.json(order)
    })
  },
})
```

```typescript
// @acme/leaderboard: bietet seine API an
export default defineServerPlugin({
  api: ctx => ({
    top: (limit: number) => ctx.db!.selectFrom(ctx.table('scores')).selectAll().orderBy('score', 'desc').limit(limit).execute(),
  }),
})
```

`api()` wird für jedes Plugin einmal aufgerufen, vor dem `setup()` aller Plugins, ein Plugin kann die API eines anderen also in seinem eigenen `setup()` verwenden, egal in welcher Reihenfolge sie laden. Auf dem Server läuft es nach den Datenbank-Migrationen, ein Plugin, das sie abgeschaltet haben, hat also keine API. Client und Server haben jeweils ihre eigenen: Die Client-API eines Plugins kann sich von seiner Server-API unterscheiden.

Um `ctx.plugin()` den Typ der API zu geben, füge sie zu `ServerPluginApis` hinzu (oder im Browser zu `ClientPluginApis`):

```typescript
declare module '@mavonengine/core/Plugins/types' {
  interface ServerPluginApis {
    '@acme/leaderboard': LeaderboardApi
  }
}
```

[`@mavonengine/mail`](/de/werkzeuge/mail), [`@mavonengine/notifications`](/de/werkzeuge/benachrichtigungen) und [`@mavonengine/auth`](/de/werkzeuge/auth#auf-dem-server) bieten ihre auf diese Weise an.

### Dateien zum Anpassen

Ein Plugin kann das Projekt einige seiner Dateien ändern lassen, etwa das Layout seiner Mails. Leg sie in ein Verzeichnis des Pakets und nenne es als `publish` im Manifest. [`mavonengine asset:publish <package>`](/de/werkzeuge/cli#mavonengine-assetpublish) kopiert sie nach `resources/<package>/` im Projekt, und das Plugin findet die Kopie des Projekts mit `ctx.publishedFile()`:

```typescript
import { readFileSync } from 'node:fs'

const layout = readFileSync(ctx.publishedFile('layout.html') ?? new URL('../publish/layout.html', import.meta.url), 'utf8')
```

`publishedFile()` ist undefined, wenn das Projekt keine Kopie hat, dann verwendet das Plugin seine eigene.

### Admin-Routen

Schütze die Admin-Routen eines Plugins mit `ctx.requireAdmin`, das das [Admin-Token](/de/netzwerk/server#admin-token) des Servers verlangt, statt dem Plugin ein eigenes Token zu geben:

```typescript
export default defineServerPlugin({
  http(app, ctx) {
    app.post('/api/my-plugin/reset', ctx.requireAdmin, (_req, res) => res.json({ reset: true }))
  },
})
```

Ein Plugin, das das Token auf anderem Weg entgegennimmt, etwa als Passwort einer Anmeldung, prüft es mit `ctx.adminToken.matches(candidate)`. `ctx.adminToken.configured` sagt, ob der Server eines hat. Das Token selbst bekommt das Plugin nie zu sehen.

### Datenbank

Mit einem [Datenbank-Plugin](/de/werkzeuge/datenbank) im Projekt ist `ctx.db` eine [Kysely](https://kysely.dev)-Instanz, die sich der Server und alle Plugins teilen, und ohne eines undefined. Ein Plugin legt seine Tabellen mit `migrations` an, die vor `setup()` laufen, und benennt sie mit `ctx.table()`, damit sich die Tabellen der Plugins nicht in die Quere kommen:

```typescript
export default defineServerPlugin({
  migrations: {
    '001_init': {
      async up(db, { table }) {
        await db.schema.createTable(table('scores'))
          .addColumn('player', 'text', c => c.primaryKey())
          .addColumn('score', 'integer', c => c.notNull().defaultTo(0))
          .execute()
      },
    },
  },
})
```

Siehe [Datenbank](/de/werkzeuge/datenbank#in-einem-plugin) für die Regeln der Migrationen und für den `database()`-Hook, der ein Plugin selbst zum Datenbank-Plugin macht. Ebenso macht ein `notify()`-Hook ein Plugin zum [Benachrichtigungs-Plugin](/de/werkzeuge/benachrichtigungen#ein-benachrichtigungs-plugin-schreiben).

### Spieler authentifizieren

Ein Auth-Plugin entscheidet, wer sich verbinden darf, bevor ein Client einen Spieler bekommt. [`@mavonengine/auth`](/de/werkzeuge/auth) ist eines, mit Accounts, Passwörtern und Sitzungen; für alles andere schreibst du dein eigenes. Sein Client-Einstiegspunkt liefert das Token, mit dem sich das Spiel verbindet, und das `authorize()` seines Server-Einstiegspunkts prüft es:

```typescript
// client.ts: wird als Authorization-Header der Verbindungsanfrage gesendet
export default defineClientPlugin({
  authorization: () => {
    const token = localStorage.getItem('session')
    return token ? `Bearer ${token}` : undefined
  },
})
```

```typescript
// server.ts
export default defineServerPlugin({
  async authorize(authorization, request, ctx) {
    const account = await findSession(ctx.db, authorization)
    if (!account)
      return false // 401
    if (account.banned)
      return 403
    return { id: account.id, name: account.username }
  },
})
```

`authorize()` gibt zurück:

| Ergebnis | |
| --- | --- |
| Eine Identität, `{ id, name?, … }` | Lässt den Client als diesen Account herein. Sie wird auch an den Client gesendet, beschränke sie also auf das, was der Spieler sehen darf |
| `true` | Lässt ihn ohne Identität herein, z.B. als Gast |
| `false` | Weist ihn mit 401 ab |
| Ein HTTP-Status von 400 bis 599 | Weist ihn mit diesem Status ab, z.B. 403 für einen gesperrten Account |

Eine Exception oder jedes andere Ergebnis weist diesen einen Client mit 500 ab, und der nächste Client wird trotzdem gefragt.

- **Die Identität lesen:** Andere Plugins verwenden `ctx.identity(channel)`, das Spiel `player.identity` auf dem Server und `network.identity` auf dem Client. Hänge alles, was eine Verbindung überdauern soll, etwa eine Stummschaltung oder einen Punktestand, an `identity.id`: `channel.id` ändert sich bei jedem erneuten Verbinden.
- **Ablehnungen auf dem Client:** Sie kommen als `connectError`-Event des [`NetworkManager`](/de/netzwerk/client#authentifizierung) an, mit dem `status`, den der Server geantwortet hat. Das Token wird gelesen, wenn ein `NetworkManager` erstellt wird; um dich nach der Anmeldung erneut zu verbinden, erstelle also einen neuen.
- **Ein Auth-Plugin:** Nur eines wird gefragt. Sind mehrere aktiviert, setz `"auth": "<package>"` in `mavonengine.json`.
- **Im Zweifel geschlossen:** Hat das Projekt ein Auth-Plugin, das nicht läuft, etwa weil eine seiner Migrationen fehlgeschlagen ist oder das in `auth` genannte Paket nicht aktiviert ist, weist der Server jeden Client mit 503 ab, statt ihn ungeprüft hereinzulassen.
- **Der Editor** verbindet sich wie ein Client und braucht mit einem Auth-Plugin daher ebenfalls ein Token. Weist der Server ihn ab, sagen die Statusleiste und das Network-Panel des Editors, warum.

Ein Hook, der eine Exception wirft, wird geloggt und für dieses Plugin abgeschaltet, und das Spiel läuft weiter.
