Mit `@mavonengine/notifications` benachrichtigt der Spielserver Spieler, und alles andere, was du benachrichtigbar machst, im Spiel und per Mail:

```typescript
await player.notify(new LevelUp(5))
```

```bash
npx @mavonengine/cli install @mavonengine/notifications
```

`player.notify()` und `notify()` gehören zur Engine, der Code des Spiels verwendet sie also ohne dieses Plugin in seiner `package.json`. Ohne Benachrichtigungs-Plugin senden sie nichts und sagen das im Log des Servers. Mit diesem Plugin erreichen sie den Spieler.

Spieler werden als ihr Account benachrichtigt, das Projekt braucht also ein Auth-Plugin wie [`@mavonengine/auth`](/de/werkzeuge/auth). Für den Kanal `mail` braucht es zusätzlich [`@mavonengine/mail`](/de/werkzeuge/mail), für den Kanal `database` ein [Datenbank-Plugin](/de/werkzeuge/datenbank).

## Eine Benachrichtigung schreiben

Eine Benachrichtigung ist eine Klasse. `via()` sagt, an welche Kanäle sie geht, und eine Methode `to<Channel>()`, was sie auf jedem sagt:

```typescript
import { Notification } from '@mavonengine/notifications/server'

export class LevelUp extends Notification {
  constructor(private level: number) {
    super()
  }

  via() {
    return ['game', 'mail']
  }

  toGame() {
    return { level: this.level }
  }

  toMail() {
    return { subject: `Level ${this.level}!`, text: `Well played: you reached level ${this.level}.` }
  }
}
```

`via()` und jedes `to<Channel>()` bekommen den Empfänger, eine Benachrichtigung kann also an manche Empfänger per Mail und an andere nur im Spiel gehen.

## Senden

```typescript
import { account, notify } from '@mavonengine/core/Notifications/Notifiable'

await player.notify(new LevelUp(5)) // ein verbundener Spieler
await notify(account(accountId), new SeasonEnded()) // ein Account, verbunden oder nicht
await notify([guildA, guildB], new WarDeclared()) // mehrere auf einmal
```

Aus einem Plugin tut `ctx.plugin('@mavonengine/notifications')?.send(to, notification)` dasselbe.

- **Ein Spieler wird als sein Account benachrichtigt:** Die Benachrichtigung erreicht jedes Spiel, das der Account offen hat, nicht nur diese eine Verbindung. Ein Spieler ohne Account, weil es kein Auth-Plugin gibt oder er ohne einen hereingelassen wurde, wird übersprungen.
- **Sie wirft, bevor sie jemanden erreicht**, wenn die Benachrichtigung einen Kanal nennt, den es nicht gibt, oder einen, für den sie kein `to<Channel>()` hat.
- **Sie erfüllt sich**, sobald jeder Kanal sie hat: im Spiel gesendet, an das Mail-Plugin übergeben oder für einen eingereihten Kanal eingereiht.

## Kanäle

### game

Über den Spiel-Socket sofort an jede offene Verbindung des Accounts des Empfängers gesendet. Ein Spieler, der nicht verbunden ist, bekommt sie nicht später; dafür gibt es den Kanal [`database`](#database). Im Browser:

```typescript
import { notifications } from '@mavonengine/notifications/client'

notifications(game).on(n => showToast(n.type, n.data))
notifications(game).onType<{ level: number }>('LevelUp', n => playFanfare(n.data.level))
```

Jede Benachrichtigung löst auch das Spiel-Event `notification` aus: `game.on('notification', n => …)`. Es hat die `id`, den `type` (den Klassennamen oder ihren statischen `notificationType`), was `toGame()` zurückgab, als `data`, und `sentAt`.

Wie eine Benachrichtigung aussieht, entscheidet das Spiel. Hier zeigt es jede als Toast, mit der Zahl der ungelesenen an einer Glocke:

![Vier Benachrichtigungen als Toasts in einem Spiel, mit der Zahl der ungelesenen an einer Glocke](/static/plugin-notifications.png)
::

### mail

Über [`@mavonengine/mail`](/de/werkzeuge/mail) gesendet, das sie einreiht, erneut versucht und unter den fehlgeschlagenen Jobs aufbewahrt, wenn sie sich nicht senden lässt. Eine Benachrichtigung mit `queued = false` wird im Aufruf gemailt. `toMail()` gibt eine ausgeschriebene Mail zurück, etwa `{ subject, text, html }`.

Die Adresse eines Accounts kommt aus [`@mavonengine/auth`](/de/werkzeuge/auth). Accounts ohne E-Mail werden nicht angeschrieben, und mit `verifiedEmailOnly` nur solche, die ihre [bestätigt](/de/werkzeuge/auth#e-mail) haben. Ohne Mail-Plugin, oder ohne Auth-Plugin für Accounts, wird der Kanal übersprungen, und das Log sagt es einmal.

### database

In der Datenbank des Servers aufbewahrt, damit der Spieler sie später liest, auch wenn er nicht verbunden war. Braucht ein [Datenbank-Plugin](/de/werkzeuge/datenbank); ohne eines wird nichts aufbewahrt, und das Log sagt es einmal. Die Tabelle ist `notifications_notifications`.

```typescript
export class FriendRequest extends Notification {
  constructor(private from: string) {
    super()
  }

  via() {
    return ['database', 'game']
  }

  toDatabase() {
    return { from: this.from }
  }

  toGame() {
    return { from: this.from }
  }
}
```

`toDatabase()` wird als JSON aufbewahrt, bis 64 KB. Jeder Empfänger bekommt eine eigene Benachrichtigung mit eigener `id`; `notificationId` ist für jeden Empfänger und Kanal eines `notify()` dieselbe und ist die `id` des Toasts im Spiel.

Im Browser liest der Spieler die Benachrichtigungen seines Accounts über die Spielverbindung, es braucht also keine eigene Anmeldung:

```typescript
import { notifications } from '@mavonengine/notifications/client'

const inbox = notifications(game)
const { notifications: list, unread } = await inbox.stored({ unread: true, limit: 20 })
await inbox.markRead([list[0].id]) // oder die id eines Toasts, oder nichts für alle

inbox.onUnread(count => setBadge(count))
```

Der Server teilt dem Spiel beim Verbinden und bei jeder Änderung die Zahl der ungelesenen mit, auch wenn der Spieler sie in einem anderen Tab gelesen hat: `inbox.unread`, `onUnread()` und das Spiel-Event `notifications:unread`. Eine Benachrichtigung wird aufbewahrt, bevor das Spiel von ihr erfährt, ein Toast lässt sich also immer als gelesen markieren.

::div{class="rounded-xl overflow-hidden shadow-2xl my-6"}
![Der Posteingang eines Spiels mit den für den Spieler aufbewahrten Benachrichtigungen, die neuesten zuerst, die ungelesenen markiert](/static/plugin-notifications-inbox.png)
::

Auf dem Server, für jeden Empfänger:

```typescript
import { account } from '@mavonengine/core/Notifications/Notifiable'
import { notifications } from '@mavonengine/notifications/server'

const inbox = notifications(server)!
await inbox.stored(account(id), { unread: true, limit: 20, offset: 0 })
await inbox.unreadCount(guild)
await inbox.markRead(account(id), ids) // ohne ids alle
await inbox.forget(account(id), ids) // löscht sie
```

Gelesene Benachrichtigungen werden `keepReadDays` nach dem Lesen gelöscht. Ungelesene bleiben.

### Eigene

```typescript
ctx.plugin('@mavonengine/notifications')?.channel('discord', {
  queued: true,
  route: to => discordWebhookOf(to),
  async send(delivery) {
    await fetch(delivery.route as string, { method: 'POST', body: JSON.stringify(delivery.payload) })
  },
})
```

Eine Benachrichtigung geht mit `'discord'` in `via()` und einem `toDiscord()` dorthin. `route()` sagt, wohin sie für einen Empfänger geht; undefined überspringt den Kanal für diesen Empfänger. Mit `queued: true` läuft `send()` auf der [Job-Warteschlange](/de/werkzeuge/warteschlange) des Servers und wird erneut versucht, wenn es wirft.

## Eigene Klassen benachrichtigbar machen

Alles mit einer stabilen ID lässt sich benachrichtigen: eine Gilde, ein Team, eine Lobby. Erweitere `notifiable()` aus der Engine, das `notify()` hinzufügt:

```typescript
import { notifiable } from '@mavonengine/core/Notifications/Notifiable'

class Guild extends notifiable(GuildRecord) {
  readonly notifiableType = 'guild'

  notifiableId() {
    return this.id
  }

  // Wohin jeder Kanal für die Gilde geht: in die Spiele ihrer Mitglieder, in die Postfächer ihrer Offiziere
  routeNotificationFor(channel: string) {
    if (channel === 'game')
      return this.memberAccountIds
    if (channel === 'mail')
      return this.officerEmails
  }
}

await guild.notify(new WarDeclared(enemy))
```

`notifiable()` ohne Klasse gibt eine eigene Basisklasse. Eine Klasse, die bereits etwas erweitert, das du nicht ändern kannst, implementiert `Notifiable` selbst, und ihr `notify()` ist eine Zeile: `return notify(this, notification)`.

`routeNotificationFor()` ist optional und geht vor der eigenen Route des Kanals. Ohne es kennen `game` und `mail` nur Accounts. Benachrichtigungen, die für andere Empfänger als Accounts aufbewahrt werden, etwa eine Gilde, lassen sich nur auf dem Server lesen.

## Optionen

Setze sie unter dem Plugin in `mavonengine.json`. Alle sind optional.

| Option | Standard | |
| --- | --- | --- |
| `verifiedEmailOnly` | `false` | Nur Accounts anschreiben, deren Adresse mit dem Link bestätigt wurde, den das Auth-Plugin mailt |
| `tries` | `3` | Wie oft die Zustellung eines eingereihten Kanals versucht wird |
| `backoffMs` | `[10000, 60000]` | Wie lange vor einem erneuten Versuch gewartet wird, in ms |
| `keepReadDays` | `90` | Aufbewahrte Benachrichtigungen so viele Tage nach dem Lesen löschen. `0` behält sie |

Mit mehr als einem aktivierten Benachrichtigungs-Plugin wählt `"notifications": "<package>"` in `mavonengine.json` das, über das `notify()` sendet.

## Ein Benachrichtigungs-Plugin schreiben

Ein Server-Plugin mit einem `notify()`-Hook ist ein Benachrichtigungs-Plugin. Es bekommt bei jedem `notify()` und `player.notify()` die Empfänger und die Benachrichtigung:

```typescript
export default defineServerPlugin({
  async notify(to, notification, ctx) {
    for (const recipient of to)
      await deliver(recipient.notifiableType, recipient.notifiableId(), notification)
  },
})
```

Erfülle es, sobald sie eingereiht oder gesendet ist: Eine Ablehnung wird an den Aufrufer von `notify()` weitergegeben. Nur das Plugin, das das Projekt gewählt hat, wird gefragt.
