Ein Spielserver hat keine Datenbank, bis das Projekt ein **Datenbank-Plugin** bekommt. Mit einem teilen sich der Server und jedes Plugin eine [Kysely](https://kysely.dev)-Instanz: `server.db` im Code des Spiels, `ctx.db` in einem Plugin. `@mavonengine/sqlite` ist das offizielle. Es verwendet das in Node eingebaute `node:sqlite`, es muss also nichts Natives kompiliert werden.

```bash
npx @mavonengine/cli install @mavonengine/sqlite
```

Die Datenbank wird beim Start des Servers unter `.mavonengine/data/mavonengine.sqlite` im Projekt angelegt. Projekte, die mit `mavonengine create` erstellt wurden, ignorieren `.mavonengine/` in git; füge es zu deiner `.gitignore` hinzu, wenn dein Projekt älter ist.

Ohne Datenbank-Plugin sind `ctx.db` und `server.db` undefined, und Plugins laufen ohne Datenbank. Nichts Datenbankbezogenes wird installiert, bis du ein Datenbank-Plugin hinzufügst: `kysely` ist eine optionale Peer-Dependency von `@mavonengine/core`.

## Optionen

Gesetzt in `mavonengine.json` unter `plugins["@mavonengine/sqlite"].options`:

| Option | Standard | |
| --- | --- | --- |
| `path` | `.mavonengine/data/mavonengine.sqlite` | Die Datenbankdatei, relativ zum Projekt-Root. `:memory:` hält sie im Speicher, sie ist weg, wenn der Server stoppt |
| `busyTimeoutMs` | `5000` | Wie lange eine Abfrage auf die Sperre einer anderen Verbindung wartet, bevor sie fehlschlägt |

`MAVONENGINE_SQLITE_PATH` überschreibt `path`, etwa um die Datenbank in Produktion auf einem Volume zu halten.

Die Datenbank läuft im WAL-Modus mit aktivierten Fremdschlüsseln.

## In einem Plugin

Jedes Server-Plugin bekommt die Datenbank als `ctx.db`. Benenne deine Tabellen mit `ctx.table()`, das ihnen den Paketnamen voranstellt, damit sich die Tabellen der Plugins nicht in die Quere kommen: `@mavonengine/chat` → `chat_mutes`, `@acme/shop` → `acme_shop_items`. Lege sie mit `migrations` an, die die Engine vor `setup()` ausführt:

```typescript
import { defineServerPlugin } from '@mavonengine/core/Plugins/types'

export default defineServerPlugin({
  migrations: {
    '001_init': {
      async up(db, { table }) {
        await db.schema.createTable(table('scores'))
          .addColumn('player', 'text', c => c.primaryKey())
          .addColumn('score', 'integer', c => c.notNull().defaultTo(0))
          .execute()
      },
    },
  },

  http(app, ctx) {
    app.get('/api/leaderboard', async (_req, res) => {
      if (!ctx.db)
        return res.status(503).json({ error: 'No database' })

      res.json(await ctx.db.selectFrom(ctx.table('scores')).selectAll().orderBy('score', 'desc').limit(10).execute())
    })
  },
})
```

### Migrationen

- Sie laufen in der Reihenfolge ihrer Namen, einmal pro Datenbank. Benenne sie so, dass sie sich sortieren lassen, etwa `001_init` und `002_add_reason`.
- Ändere oder benenne nie eine Migration um, die ausgeliefert wurde; füge stattdessen eine neue hinzu.
- Jede Migration läuft in einer Transaktion. Schlägt eine fehl, wird sie zurückgerollt und das Plugin bis zum nächsten Start abgeschaltet.
- Welche gelaufen sind, wird pro Plugin in `<prefix>__migrations` festgehalten.
- Ohne Datenbank-Plugin werden sie übersprungen, und der Server warnt, dass das Plugin ohne Datenbank läuft.

### Gut zu wissen

- **Keine Datenbank:** `ctx.db` ist undefined, wenn das Projekt kein Datenbank-Plugin hat. Prüfe darauf und arbeite ohne Datenbank weiter, wenn dein Plugin das kann.
- **Geteilte Instanz:** Zerstöre `ctx.db` nicht, da alle Plugins sie teilen. Die Engine schließt sie, wenn der Server stoppt, nachdem das `destroy()` jedes Plugins fertig ist. `destroy()` darf ein Promise zurückgeben, ein Plugin kann also noch speichern, was es hat.
- **Portables SQL:** Bleib bei SQL, das in allen Datenbanken funktioniert, damit dein Plugin auch mit anderen Datenbank-Plugins als SQLite läuft. SQLite speichert Booleans als `0`/`1` und Daten als ISO-Strings und liest sie auch so wieder aus.
- **Kysely:** Füge `kysely` als Dev-Dependency hinzu, für seine Typen und für `sql`.

## Im Server-Code des Spiels

Das Spiel bekommt dieselbe Datenbank als `server.db`, sobald `start()` aufgelöst ist. Benenne seine Tabellen so, dass sie nicht mit dem Präfix eines Plugins beginnen, z.B. `game_scores`:

```typescript
await server.start()

const top = await server.db?.selectFrom('game_scores').selectAll().orderBy('score', 'desc').limit(10).execute()
```

`server.stop()` gibt ein Promise zurück, das erfüllt ist, sobald die Datenbank geschlossen ist. Bei `SIGINT` und `SIGTERM` beendet sich der Server selbst auf diese Weise, siehe [Beenden](/de/netzwerk/server#beenden).

## Hineinschauen

Die Datenbank enthält, was Spieler getan haben, der Server zeigt sie also nur mit seinem [Admin-Token](/de/netzwerk/server#admin-token); ohne Token antwortet er nur auf dem Rechner des Servers selbst. Alles Folgende liest nur.

- Der **Database**-Tab des [Dashboards](/de/werkzeuge/monitoring#database) listet die Tabellen mit dem Plugin, zu dem jede gehört, ihre Zeilen und die gelaufenen Migrationen.
- `GET /api/game/database` und `GET /api/game/database/tables/:name` sind das, was er liest, siehe [Eingebaute Endpunkte](/de/netzwerk/server#eingebaute-endpunkte).
- Mit den Tools `database_overview` und `database_rows` des [MCP-Servers](/de/werkzeuge/ki-assistenten#datenbank-tools) kann ein Assistent sie lesen, wobei geheim aussehende Spalten geschwärzt werden.

## Mehr als ein Datenbank-Plugin

Sind mehrere Datenbank-Plugins aktiviert, nenne das zu verwendende in `mavonengine.json` (oder als `database` in den Optionen des Servers):

```json
{
  "database": "@mavonengine/sqlite",
  "plugins": { "@mavonengine/sqlite": {} }
}
```

## Außerhalb eines Spielservers

Für Skripte und Tests öffnet `openSqlite(path)` eine Datenbank auf dieselbe Weise:

```typescript
import { openSqlite } from '@mavonengine/sqlite'

const db = openSqlite('.mavonengine/data/mavonengine.sqlite')
const mutes = await db.selectFrom('chat_mutes').selectAll().execute()
await db.destroy()
```

## Ein Datenbank-Plugin schreiben

Ein Server-Plugin mit einem `database()`-Hook ist ein Datenbank-Plugin. Er gibt die Kysely-Instanz zurück, die der Server und seine Plugins verwenden:

```typescript
export default defineServerPlugin({
  database(ctx) {
    return new Kysely({ dialect: myDialect(ctx.options) })
  },
})
```

Er wird einmal aufgerufen, vor den Migrationen und dem `setup()` aller Plugins, und nur für das Plugin, das das Projekt ausgewählt hat. Die Engine zerstört die Instanz, wenn der Server stoppt.
