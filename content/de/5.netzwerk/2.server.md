Die `Server`-Klasse ist der autoritative Multiplayer-Server. Sie erstellt das headless `BaseGame`, verwaltet Client-Verbindungen, verarbeitet Befehle, sendet den Weltzustand und liefert den Spiel-Client und seine HTTP-API aus.

## Setup

```typescript
import type { ServerChannel } from '@geckos.io/server'
import BaseServer from '@mavonengine/core/Networking/Server/Server'
import Player from './Server/Entities/Player'

export default class Server extends BaseServer<Player> {
  protected onConnection(channel: ServerChannel): Player {
    // Ein neuer Client hat sich verbunden: gib seinen Spieler zurück, der Server fügt ihn der Welt hinzu
    return new Player(channel.id)
  }

  protected onCommand(command: any, delta: number): void {
    // Einen eingehenden Client-Befehl verarbeiten
  }

  getStateSyncDistance(): number {
    // Sichtbarkeitsradius (Einheiten) für den Zustandsabgleich zurückgeben
    return 200
  }
}
```

```typescript
import RAPIER from '@dimforge/rapier3d-compat'

RAPIER.init().then(() => {
  const physicsWorld = new RAPIER.World({ x: 0, y: -9.83, z: 0 })

  const server = new Server(logger, physicsWorld, {
    client: { root: clientDir, dev: process.env.MAVONENGINE_DEV_CLIENT === '1' },
    plugins: { root: projectRoot },
  })

  server.start().then(() => server.openScene('main'))
})
```

Der Konstruktor nimmt einen winston-Logger, eine optionale Rapier-Welt (siehe [Physik](/de/kernkonzepte/physik)) und die unten aufgeführten Optionen. Innerhalb des Servers ist das Spiel `this.game`; anderswo verwendest du `Server.instance()`.

`start()` gibt ein Promise zurück: Mit `plugins: { root }` werden zuerst die Plugins importiert, und die [Datenbank-Migrationen](/de/werkzeuge/datenbank#migrationen) der Plugins laufen vor ihrem `setup()`, also warte darauf, bevor du dich auf sie oder auf `server.db` verlässt.

## Optionen

| Option | Standard | Beschreibung |
|--------|---------|-------------|
| `httpPort` | `8050` | Port des HTTP-Servers |
| `client` | | Den Spiel-Client ausliefern: `{ root, dev?, dist? }`. Mit `dev` wird der Quellcode über Vite mit Hot Reload ausgeliefert, sonst das gebaute `<root>/dist` |
| `socketPort` | keiner, wenn `client` gesetzt ist, sonst `8081` | Separater Port für den geckos.io-Spiel-Socket, oder `false` |
| `plugins` | | `{ root }`, um die in `<root>/mavonengine.json` aktivierten Plugins zu laden, oder Plugin-Objekte. Siehe [Plugins](/de/werkzeuge/plugins) |
| `root` | `plugins.root` | Projekt-Root mit `scenes/`, wird von `openScene()` verwendet |
| `metrics` | | `{ enabled, token, logBufferSize, requestLogSize, logIntervalMs }`, siehe [Monitoring](/de/werkzeuge/monitoring) |
| `adminToken` | `$MAVONENGINE_ADMIN_TOKEN` | Das [Admin-Token](#admin-token) des Servers |
| `latencySimulation` | | `{ fixedLatency, jitter, packetLoss }`, siehe [Latenzsimulation](#latenzsimulation) |
| `database` | `database` in `mavonengine.json`, sonst das erste | Paket des zu verwendenden [Datenbank-Plugins](/de/werkzeuge/datenbank), wenn mehrere aktiviert sind |
| `auth` | `auth` in `mavonengine.json`, sonst das erste | Paket des zu verwendenden [Auth-Plugins](/de/werkzeuge/plugins#spieler-authentifizieren), wenn mehrere aktiviert sind |
| `notifications` | `notifications` in `mavonengine.json`, sonst das erste | Paket des [Benachrichtigungs-Plugins](/de/werkzeuge/benachrichtigungen), über das `notify()` sendet, wenn mehr als eines aktiviert ist |
| `appUrl` | `appUrl` in `mavonengine.json` | Wo das Spiel ist, für Links, die aus ihm hinausführen, etwa in Mails. `MAVONENGINE_APP_URL` überschreibt beides. Plugins bekommen es als `ctx.appUrl` |
| `appName` | `appName` in `mavonengine.json` | Der Name des Spiels, z. B. in Mails. Plugins bekommen ihn als `ctx.appName` |
| `queue` | | `{ driver, work, concurrency, queues, pollIntervalMs, retryAfterMs }`, siehe [Job-Warteschlange](/de/werkzeuge/warteschlange#optionen) |
| `stopOnSignals` | `true` | Bei `SIGINT` und `SIGTERM` sauber beenden, siehe [Beenden](#beenden) |

## Ports

Wenn der Server den Client ausliefert, läuft alles auf **einem Port** (standardmäßig `8050`): der Client, der Spiel-Socket und die HTTP-API. Der Client braucht keinen zweiten Origin, was das Deployment hinter einem Reverse Proxy einfach macht.

| Port | Zweck |
|------|---------|
| `8050` | HTTP-Server: Client, API und der Spiel-Socket |
| `8081` | Separater geckos.io-Socket, nur wenn der Client nicht ausgeliefert wird oder `socketPort` gesetzt ist |

## Zu implementierende Methoden

| Methode | Beschreibung |
|--------|-------------|
| `onConnection(channel)` | Wird aufgerufen, wenn ein neuer Client sich verbindet; gib seine Spieler-Entity zurück |
| `onCommand(command, delta)` | Wird für jeden gepufferten Befehl bei jedem Tick aufgerufen |
| `getStateSyncDistance()` | Gibt die maximale Distanz für die Sichtbarkeit im Zustandsabgleich zurück |
| `onTick(delta)` | Optional, läuft bei jedem Tick, nachdem die Befehle verarbeitet wurden |

## Befehlspuffer

Clients senden Befehle (z.B. Eingabe-Frames) mit einer Sequenz-ID. Der Server stellt sie in eine Warteschlange, sortiert sie nach Sequenz-ID und verarbeitet sie bei jedem Tick der Reihe nach über `onCommand`. Nachdem ein Befehl ausgeführt wurde, wird die `lastProcessedSequenceId` des Spielers aktualisiert und im Zustandsabgleich zurückgesendet, damit der Client die Eingaben verwerfen kann, die der Server bereits angewendet hat. Jedes Zustandsupdate trägt sie außerdem als `ack`, neben dem Server-`tick`, in dem es erstellt wurde, siehe [Zustandspaket-Format](/de/netzwerk/zustandssync#zustandspaket-format).

## Szenen

```typescript
server.openScene('main')               // <root>/scenes/main.json
server.openScene('main', { watch: true })
```

Es werden nur die Szenenobjekte mit einer `server`-Factory gebaut. Solange der Client über Vite ausgeliefert wird, wird die Datei beobachtet und neu geladen, wenn der [Editor](/de/kernkonzepte/level-editor) sie speichert. Siehe [Szenen](/de/kernkonzepte/szenen).

## Datenbank

Mit einem [Datenbank-Plugin](/de/werkzeuge/datenbank) wie `@mavonengine/sqlite` ist `server.db` eine [Kysely](https://kysely.dev)-Instanz, die mit den Plugins geteilt wird. Ohne eines, und bis `start()` aufgelöst ist, ist sie undefined. Benenne die eigenen Tabellen des Spiels so, dass sie nicht mit dem Präfix eines Plugins beginnen, z.B. `game_scores`. `server.databaseProvider` ist das Paket des verwendeten Plugins.

## Job-Warteschlange

`server.queue` führt Jobs im Hintergrund des Servers aus, mit Wiederholungen, Backoff und Verzögerungen. Jobs können vor `start()` eingereiht werden und laufen, sobald es fertig ist. Sie liegen mit einem Datenbank-Plugin in der Datenbank, sonst im Speicher. Siehe [Job-Warteschlange](/de/werkzeuge/warteschlange).

```typescript
await server.queue.dispatch(new GrantReward({ player: account.id, coins: 10 }))
```

## Wer verbunden ist

Mit einem Auth-Plugin wie [`@mavonengine/auth`](/de/werkzeuge/auth) wird ein Client geprüft, bevor er einen Spieler bekommt, und mit einem HTTP-Status abgewiesen, wenn er sich nicht verbinden darf. `player.identity` ist dann, wer der Spieler ist, so wie es das Auth-Plugin beim Verbinden gesagt hat:

```typescript
protected onConnection(channel: ServerChannel): Player {
  const player = new Player(channel.id)

  // { id, name?, … }: dieselbe ID bei jedem erneuten Verbinden, anders als channel.id
  const account = player.identity
  if (account)
    loadSave(player, account.id)

  return player
}
```

Sie ist undefined ohne Auth-Plugin, für einen Client, den das Plugin ohne Identität hereingelassen hat, und für Bots. Der Server loggt die Identität bei jeder Verbindung, und die Metriken geben jedem Spieler seinen Account als `{ id, name, guest }`. `server.authProvider` ist das Paket des verwendeten Auth-Plugins. Siehe [Spieler authentifizieren](/de/werkzeuge/plugins#spieler-authentifizieren), um eines zu schreiben.

`player.notify(notification)` benachrichtigt den Account des Spielers über das [Benachrichtigungs-Plugin](/de/werkzeuge/benachrichtigungen) des Projekts, auf jeder Verbindung, die der Account offen hat. Ein Spieler ohne Identität wird übersprungen, und ohne Benachrichtigungs-Plugin wird nichts gesendet, und das Log sagt es. `server.notificationsProvider` ist das Paket des verwendeten Benachrichtigungs-Plugins.

## Editor-Clients

Ein Client, der den Level-Editor startet, teilt das dem Server mit. Der Server entfernt seinen Spieler, zählt ihn nicht mehr als Spieler und sendet ihm alle Entities der Welt. Ihre Channel-IDs stehen in `server.editorChannels`.

Ein Server in Produktion (`NODE_ENV=production`) ignoriert Clients, die den Editor anhängen wollen, da der Editor die ganze Welt gesendet bekommt. Mit einem Auth-Plugin braucht der Editor eine Sitzung wie jeder Client; die Statusleiste des Editors sagt, warum, wenn der Server ihn abweist.

## HTTP-Endpunkte

Registriere eigene HTTP-Routen mit `onHttp`, bevor du `start()` aufrufst:

```typescript
server.onHttp((app) => {
  app.get('/api/status', (req, res) => {
    res.json({ players: server.game.world.entities.items.size })
  })
})
```

Deine Routen laufen vor den Plugin-Routen und vor dem Spiel-Client, der alle übrigen Seitenanfragen beantwortet.

### Routen beschreiben

`GET /api/game/routes` listet jede Route des Servers, gelesen aus der laufenden Express-App: Methode, Pfad, Pfadparameter, ob die Engine, das Spiel oder ein Plugin sie registriert hat, und ob sie nur in der Entwicklung existiert. Der Routes-Tab des [Dashboards](/de/werkzeuge/monitoring#routes) und die Server-Ansicht des [Editors](/de/kernkonzepte/level-editor#server-und-plugins) zeigen diese Liste.

Eine Route wird aufgeführt, ohne irgendwo deklariert zu werden. Um zu sagen, was sie tut, setz `describeRoute()` vor den Handler. Alles darin ist optional:

```typescript
import { describeRoute } from '@mavonengine/core/Networking/Server/Http/RouteCatalog'

server.onHttp((app) => {
  app.get('/api/scores/:id', describeRoute({
    summary: 'One score',
    params: { id: 'Id of the player' },
    response: '`{ score }`',
  }), handler)
})
```

Es nimmt `summary`, `description`, `params`, `query`, `response`, `auth` und `devOnly`. Übergib `devOnly: true` für eine Route, die du nur in der Entwicklung registrierst: Eine Route ohne diese Angabe wird als auch in Produktion ausgeliefert aufgeführt.

### Admin-Token

Ein Spielserver hat ein einziges Admin-Token, für alles, was ihn verändert oder verrät, was nicht jeder wissen soll. Die Engine und jedes Plugin verwenden dasselbe, kein Plugin braucht also ein eigenes Geheimnis:

```bash
MAVONENGINE_ADMIN_TOKEN=… npm start
```

oder `adminToken` in den Optionen des Servers. Anfragen senden es als `Authorization: Bearer <token>`. Ohne Token antworten Admin-Routen nur auf Anfragen von localhost.

Schütze deine eigenen Admin-Routen mit `server.http.requireAdmin`:

```typescript
server.onHttp((app) => {
  app.post('/api/restart-round', server.http.requireAdmin, (_req, res) => res.json({ ok: true }))
})
```

- Das Token liest auch die Metrik-Endpunkte und schaltet sie in Produktion ein, `mavonengine dashboard` und `mavonengine mcp` nehmen es also für `--token`. Das Metrik-Token bleibt schreibgeschützt.
- Plugins bekommen denselben Schutz als `ctx.requireAdmin`, siehe [Plugins](/de/werkzeuge/plugins#admin-routen). [`@mavonengine/chat`](/de/werkzeuge/chat#admin-api) und [`@mavonengine/auth`](/de/werkzeuge/auth#routen) schützen damit ihre Admin-APIs, und [`@mavonengine/http-monitoring`](/de/werkzeuge/monitoring#anmeldung) nimmt es als Passwort seiner Anmeldung.
- Die Datenbank-Endpunkte nehmen nur das Admin-Token, da die Datenbank enthält, was Spieler getan haben.
- Routen hinter dem Schutz geben in der Routenliste an, wer sie aufrufen darf.

### Eingebaute Endpunkte

| Pfad | Beschreibung |
|------|-------------|
| `GET /api/game/health` | Health-Check |
| `GET /api/game/metrics` | Metrik-Snapshot (Tick-Zeit, CPU, Bandbreite, Spieler, Welt, Physik, Job-Warteschlange) |
| `GET /api/game/logs` | Aktuelle Server-Logeinträge |
| `GET /api/game/requests` | Aktuelle HTTP-Anfragen |
| `GET /api/game/routes` | Jede HTTP-Route des Servers |
| `GET /api/game/plugins` | Die Plugins des Projekts: Version, Ziel, Prefabs, ob der Server-Einstiegspunkt jedes Plugins läuft und welches das Datenbank-, das Auth- und das Benachrichtigungs-Plugin ist |
| `GET /api/game/database` | Das Datenbank-Plugin, jede Tabelle mit dem Plugin, zu dem sie gehört, ihren Spalten und ihrer Zeilenzahl, und die Migrationen, die jedes Plugin ausgeführt hat. Admin-Token |
| `GET /api/game/database/tables/:name` | Eine Seite der Zeilen einer Tabelle, mit `?offset=` und `?limit=` (Standard 50, höchstens 500). Admin-Token |
| `GET /api/game/dev/*` | Inspektion von Szene und Entities, nur in der Entwicklung |
| `GET /api/game/dev/net/*` | Aufgezeichnete Pakete (`/packets`, `/packets/:id`) und wer was gesendet bekommt (`/sync`), nur in der Entwicklung. Siehe [Netzwerk-Debugging](/de/netzwerk/zustandssync#netzwerk-debugging) |

Die Endpunkte für Metriken, Logs, Anfragen, Routen und Plugins antworten nur localhost, solange kein Token gesetzt ist. Siehe [Monitoring](/de/werkzeuge/monitoring).

## Latenzsimulation

Teste deinen Netcode gegen eine schlechte Verbindung. Der Server verzögert Pongs, Zustandsupdates und eingehende Befehle:

```typescript
const server = new Server(logger, physicsWorld, {
  latencySimulation: {
    fixedLatency: 100, // ms
    jitter: 30,        // ms
    packetLoss: 0.05,  // 0 - 1
  },
})
```

Der Server loggt beim Start eine Warnung, solange die Simulation aktiv ist. Liefere sie niemals aktiviert aus.

## Bandbreitenverfolgung

Der Server verfolgt gesendete und empfangene Bandbreite. Greife über `server.bandwidthTracker` darauf zu, oder über `server.metrics` auf alle Metriken. Die Werte stammen aus den Byte-Zählern der WebRTC-Verbindungen selbst und umfassen daher alles auf der Verbindung, nicht nur Zustandsupdates und Befehle.

## ServerWorld

Die Welt des Servers ist eine `ServerWorld`, die `BaseWorld` erweitert und Player-Verwaltung für verbundene Clients hinzufügt (`world.players`).

Der Server pflegt eine eigene Three.js-Szene mit **vereinfachten Hitbox-Meshes** statt vollständiger visueller Geometrie. Das hält Speicher- und CPU-Aufwand gering und ermöglicht gleichzeitig autoritative Raycasts, Treffererkennung und räumliche Abfragen direkt gegen die Szene — ohne den vom Client gemeldeten Positionen vertrauen zu müssen.

## Beenden

`server.stop()` stoppt die Metrik-Timer, den Szenen-Watcher, die [Job-Warteschlange](/de/werkzeuge/warteschlange) und die Plugins und schließt dann die Datenbank. Es gibt ein Promise zurück, das erfüllt ist, sobald die Datenbank geschlossen ist, nachdem die laufenden Jobs und das `destroy()` jedes Plugins fertig sind, und das nie ablehnt.

Der Server beendet sich selbst auf diese Weise, wenn der Prozess `SIGINT` (Strg+C) oder `SIGTERM` (ein Deployment, `docker stop`, ein Neustart durch `mavonengine dev`) bekommt, und der Prozess endet danach. Ist er nach 2,5 Sekunden nicht gestoppt, endet der Prozess trotzdem. Übergib `stopOnSignals: false`, wenn das Spiel diese Signale selbst behandelt, und ruf dort `stop()` auf. Windows kennt kein `SIGTERM`: Ein dort beendeter Prozess stoppt ohne das.
