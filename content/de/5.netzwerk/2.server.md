Die `Server`-Klasse ist der autoritative Multiplayer-Server. Sie erstellt das headless `BaseGame`, verwaltet Client-Verbindungen, verarbeitet Befehle, sendet den Weltzustand und liefert den Spiel-Client und seine HTTP-API aus.

## Setup

```typescript
import type { ServerChannel } from '@geckos.io/server'
import BaseServer from '@mavonengine/core/Networking/Server/Server'
import Player from './Server/Entities/Player'

export default class Server extends BaseServer<Player> {
  protected onConnection(channel: ServerChannel): Player {
    // Ein neuer Client hat sich verbunden: gib seinen Spieler zurück, der Server fügt ihn der Welt hinzu
    return new Player(channel.id)
  }

  protected onCommand(command: any, delta: number): void {
    // Einen eingehenden Client-Befehl verarbeiten
  }

  getStateSyncDistance(): number {
    // Sichtbarkeitsradius (Einheiten) für den Zustandsabgleich zurückgeben
    return 200
  }
}
```

```typescript
import RAPIER from '@dimforge/rapier3d-compat'

RAPIER.init().then(() => {
  const physicsWorld = new RAPIER.World({ x: 0, y: -9.83, z: 0 })

  const server = new Server(logger, physicsWorld, {
    client: { root: clientDir, dev: process.env.MAVONENGINE_DEV_CLIENT === '1' },
    plugins: { root: projectRoot },
  })

  server.start().then(() => server.openScene('main'))
})
```

Der Konstruktor nimmt einen winston-Logger, eine optionale Rapier-Welt (siehe [Physik](/de/kernkonzepte/physik)) und die unten aufgeführten Optionen. Innerhalb des Servers ist das Spiel `this.game`; anderswo verwendest du `Server.instance()`.

`start()` gibt ein Promise zurück: Mit `plugins: { root }` werden zuerst die Plugins importiert, also warte darauf, bevor du dich auf sie verlässt.

## Optionen

| Option | Standard | Beschreibung |
|--------|---------|-------------|
| `httpPort` | `8050` | Port des HTTP-Servers |
| `client` | | Den Spiel-Client ausliefern: `{ root, dev?, dist? }`. Mit `dev` wird der Quellcode über Vite mit Hot Reload ausgeliefert, sonst das gebaute `<root>/dist` |
| `socketPort` | keiner, wenn `client` gesetzt ist, sonst `8081` | Separater Port für den geckos.io-Spiel-Socket, oder `false` |
| `plugins` | | `{ root }`, um die in `<root>/mavonengine.json` aktivierten Plugins zu laden, oder Plugin-Objekte. Siehe [Plugins](/de/werkzeuge/plugins) |
| `root` | `plugins.root` | Projekt-Root mit `scenes/`, wird von `openScene()` verwendet |
| `metrics` | | `{ enabled, token, logBufferSize, requestLogSize, logIntervalMs }`, siehe [Monitoring](/de/werkzeuge/monitoring) |
| `latencySimulation` | | `{ fixedLatency, jitter, packetLoss }`, siehe [Latenzsimulation](#latenzsimulation) |

## Ports

Wenn der Server den Client ausliefert, läuft alles auf **einem Port** (standardmäßig `8050`): der Client, der Spiel-Socket und die HTTP-API. Der Client braucht keinen zweiten Origin, was das Deployment hinter einem Reverse Proxy einfach macht.

| Port | Zweck |
|------|---------|
| `8050` | HTTP-Server: Client, API und der Spiel-Socket |
| `8081` | Separater geckos.io-Socket, nur wenn der Client nicht ausgeliefert wird oder `socketPort` gesetzt ist |

## Zu implementierende Methoden

| Methode | Beschreibung |
|--------|-------------|
| `onConnection(channel)` | Wird aufgerufen, wenn ein neuer Client sich verbindet; gib seine Spieler-Entity zurück |
| `onCommand(command, delta)` | Wird für jeden gepufferten Befehl bei jedem Tick aufgerufen |
| `getStateSyncDistance()` | Gibt die maximale Distanz für die Sichtbarkeit im Zustandsabgleich zurück |
| `onTick(delta)` | Optional, läuft bei jedem Tick, nachdem die Befehle verarbeitet wurden |

## Befehlspuffer

Clients senden Befehle (z.B. Eingabe-Frames) mit einer Sequenz-ID. Der Server stellt sie in eine Warteschlange, sortiert sie nach Sequenz-ID und verarbeitet sie bei jedem Tick der Reihe nach über `onCommand`. Nachdem ein Befehl ausgeführt wurde, wird die `lastProcessedSequenceId` des Spielers aktualisiert und im Zustandsabgleich zurückgesendet, damit der Client die Eingaben verwerfen kann, die der Server bereits angewendet hat.

## Szenen

```typescript
server.openScene('main')               // <root>/scenes/main.json
server.openScene('main', { watch: true })
```

Es werden nur die Szenenobjekte mit einer `server`-Factory gebaut. Solange der Client über Vite ausgeliefert wird, wird die Datei beobachtet und neu geladen, wenn der [Editor](/de/kernkonzepte/level-editor) sie speichert. Siehe [Szenen](/de/kernkonzepte/szenen).

## Editor-Clients

Ein Client, der den Level-Editor startet, teilt das dem Server mit. Der Server entfernt seinen Spieler, zählt ihn nicht mehr als Spieler und sendet ihm alle Entities der Welt. Ihre Channel-IDs stehen in `server.editorChannels`.

## HTTP-Endpunkte

Registriere eigene HTTP-Routen mit `onHttp`, bevor du `start()` aufrufst:

```typescript
server.onHttp((app) => {
  app.get('/api/status', (req, res) => {
    res.json({ players: server.game.world.entities.items.size })
  })
})
```

Deine Routen laufen vor den Plugin-Routen und vor dem Spiel-Client, der alle übrigen Seitenanfragen beantwortet.

Eingebaute Endpunkte:

| Pfad | Beschreibung |
|------|-------------|
| `GET /api/game/health` | Health-Check |
| `GET /api/game/metrics` | Metrik-Snapshot (Tick-Zeit, CPU, Bandbreite, Spieler, Welt, Physik) |
| `GET /api/game/logs` | Aktuelle Server-Logeinträge |
| `GET /api/game/requests` | Aktuelle HTTP-Anfragen |
| `GET /api/game/dev/*` | Inspektion von Szene und Entities, nur in der Entwicklung |

Die Endpunkte für Metriken, Logs und Anfragen antworten nur localhost, solange kein Token gesetzt ist. Siehe [Monitoring](/de/werkzeuge/monitoring).

## Latenzsimulation

Teste deinen Netcode gegen eine schlechte Verbindung. Der Server verzögert Pongs, Zustandsupdates und eingehende Befehle:

```typescript
const server = new Server(logger, physicsWorld, {
  latencySimulation: {
    fixedLatency: 100, // ms
    jitter: 30,        // ms
    packetLoss: 0.05,  // 0 - 1
  },
})
```

Der Server loggt beim Start eine Warnung, solange die Simulation aktiv ist. Liefere sie niemals aktiviert aus.

## Bandbreitenverfolgung

Der Server verfolgt gesendete und empfangene Bandbreite. Greife über `server.bandwidthTracker` darauf zu, oder über `server.metrics` auf alle Metriken.

## ServerWorld

Die Welt des Servers ist eine `ServerWorld`, die `BaseWorld` erweitert und Player-Verwaltung für verbundene Clients hinzufügt (`world.players`).

Der Server pflegt eine eigene Three.js-Szene mit **vereinfachten Hitbox-Meshes** statt vollständiger visueller Geometrie. Das hält Speicher- und CPU-Aufwand gering und ermöglicht gleichzeitig autoritative Raycasts, Treffererkennung und räumliche Abfragen direkt gegen die Szene — ohne den vom Client gemeldeten Positionen vertrauen zu müssen.

## Beenden

`server.stop()` stoppt die Metrik-Timer, den Szenen-Watcher und die Plugins.
