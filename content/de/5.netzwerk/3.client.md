`NetworkManager` verwaltet die client-seitige WebRTC-Verbindung zum Server über [geckos.io](https://github.com/geckosio/geckos.io).

## Instanz erstellen und abrufen

Leite davon mit geckos.io-Client-Optionen ab. Wenn der Spielserver den Client ausliefert, verbinde dich mit dem eigenen Origin und Port der Seite, so wie es das Multiplayer-Template macht:

```typescript
import BaseNetworkManager from '@mavonengine/core/Networking/Client/NetworkManager'

export default class NetworkManager extends BaseNetworkManager {
  constructor() {
    super({
      // @ts-expect-error null verwendet den eigenen Port der Seite
      port: null,
      url: '/socket',
    })
  }
}
```

`NetworkManager` ist ein Singleton:

```typescript
const network = NetworkManager.getInstance()

// Wird auch am Spiel gesetzt, für Dev-Tools
Game.instance().network
```

## Eigenschaften

| Eigenschaft | Typ | Beschreibung |
|----------|------|-------------|
| `socket` | `geckos.io socket` | Der zugrunde liegende WebRTC-Socket |
| `ping` | `number` | Aktuelle Round-Trip-Latenz in Millisekunden |
| `connected` | `boolean` | Ob der Client mit dem Server verbunden ist |
| `editorMode` | `boolean` | Ob dieser Client den Editor ausführt und daher auf dem Server kein Spieler ist |
| `identity` | `Identity \| undefined` | Als wen das Auth-Plugin des Servers diesen Client hereingelassen hat, sobald er verbunden ist. Siehe [Authentifizierung](#authentifizierung) |
| `connectError` | `ConnectError \| null` | Warum der letzte Verbindungsversuch fehlgeschlagen ist, `null` davor und sobald verbunden |
| `serverView` | `ServerView` | Was der Server zuletzt gesendet hat, unberührt von Interpolation oder Vorhersage, siehe [unten](#die-sicht-des-servers) |
| `net` | `NetRecorder` | Die letzten Pakete und Netzwerk-Events dieses Clients, für die Dev-Tools. Siehe [Netzwerk-Debugging](/de/netzwerk/zustandssync#netzwerk-debugging) |

## Befehle an den Server senden

Sende Befehle über `sendCommand`. Es vergibt die nächste Sequenz-ID und behält den Befehl für das erneute Abspielen in einer lokalen Warteschlange:

```typescript
network.sendCommand({
  type: ClientCommand.CL_MOVE,
  keys: [...input.keysPressed],
  yaw,
})
```

## Reconciliation

Der Server sendet die `lastProcessedSequenceId` jedes Spielers im Zustandsabgleich mit. Verwirf die Befehle, die der Server bereits angewendet hat; die in der Warteschlange verbleibenden sind diejenigen, die der Server noch nicht gesehen hat und die du auf Basis der Server-Position erneut abspielen kannst:

```typescript
network.dropCommandsAtSequenceId(player.lastProcessedSequenceId)
```

## Zustand vom Server empfangen

Lausche auf dem Socket, sobald die Verbindung steht, z.B. in `onConnect()`:

```typescript
protected override onConnect() {
  super.onConnect()

  this.socket.on(ServerCommand.SV_STATE, (data) => {
    // Server-Zustand auf lokale Entities anwenden, siehe Zustandsabgleich
  })
}
```

## Die Sicht des Servers

`network.serverView` hält fest, was das letzte Zustandsupdate über sich selbst gesagt hat:

| Feld | Beschreibung |
|-------|-------------|
| `tick` | Server-Tick des letzten Zustands, `null`, bis der erste angekommen ist |
| `serverTime` | Epoch-ms auf dem Server, als der Zustand erstellt wurde |
| `ack` | Letzte Eingabe dieses Clients, die der Server verarbeitet hatte, `null` für den Editor |
| `receivedAt` | `performance.now()` bei der Ankunft |
| `missedStates` | Zustände, die nie angekommen sind, gezählt anhand von Lücken in den Tick-Nummern |
| `entities` | Roher Server-Zustand pro Entity-ID. Wird nur gefüllt, während `net` aufzeichnet, für die Dev-Tools |

Ein Zustand, der nach einem neueren ankommt, wird hier ignoriert: Der Datenkanal ist ungeordnet.

## Authentifizierung

Hat der Server ein Auth-Plugin wie [`@mavonengine/auth`](/de/werkzeuge/auth), trägt die Verbindungsanfrage einen `Authorization`-Header, den es prüft. Der Client-Einstiegspunkt des Plugins liefert ihn, ein Spiel übergibt also normalerweise nichts. Ein Spiel, das das Token selbst verwaltet, übergibt `authorization` in den Optionen:

```typescript
super({
  port: null,
  url: '/socket',
  authorization: `Bearer ${token}`,
})
```

Das Token wird gelesen, wenn der `NetworkManager` erstellt wird, und der Client versucht es nach einer Ablehnung nicht erneut: Erstelle einen neuen, um dich nach dem An- oder Abmelden erneut zu verbinden.

Sobald verbunden, ist `network.identity`, als wen der Server diesen Client hereingelassen hat (`{ id, name?, … }`). Sie ist undefined, wenn der Server kein Auth-Plugin hat oder den Client ohne Identität hereingelassen hat.

Eine Ablehnung kommt als `connectError`-Event und im Hook `onConnectError()` an, mit dem HTTP-Status, den der Server geantwortet hat:

```typescript
network.on('connectError', (error) => {
  if (error.status === 401)
    showLogin() // keine gültige Sitzung
})
```

| `status` | |
| --- | --- |
| `401` | Keine gültige Sitzung: erneut anmelden |
| `403` | Der Account darf sich nicht verbinden, z.B. weil er deaktiviert ist |
| `503` | Der Server hat ein Auth-Plugin, das nicht läuft, und weist daher jeden Client ab |
| keiner | Die Verbindung ist aus einem anderen Grund fehlgeschlagen, siehe `message` |

`network.connectError` behält den letzten Fehler für alle, die erst danach nachsehen.

## Editor-Modus

Wenn der [Level-Editor](/de/kernkonzepte/level-editor) startet, bleibt die Verbindung offen und der Client meldet sich als Editor an. Der Server entfernt dann seinen Spieler und sendet ihm die ganze Welt, sodass andere Spieler während des Bearbeitens weiter angezeigt werden.

## Verbindungs-Events

Überschreibe `onConnect()`, `onDisconnect()`, `onConnectError()` und `onPong()` in deiner Unterklasse, um auf die Verbindung zu reagieren. `onConnect()` muss `super.onConnect()` aufrufen, das die Ping-Prüfungen startet. `NetworkManager` erweitert `EventEmitter`, du kannst also per `trigger()` weitergeben, was du empfängst, damit der Rest deines Spiels darauf lauschen kann.

### Warum eine Verbindung abbrach

`onDisconnect(info)` und das Event `disconnect` bekommen eine `DisconnectInfo`, um einen Netzwerkabbruch von einem Schließen zu unterscheiden:

| Feld | |
|------|---|
| `closedByClient` | Dieser Client hat sie geschlossen, über `destroy()` |
| `connectionState` / `iceConnectionState` | Der Zustand der WebRTC-Peer-Verbindung: `disconnected` (keine Pakete mehr), `failed` oder `closed` |
| `connectedFor` | Wie lange sie bestand, in ms. `null`, wenn sie nie zustande kam |
| `lastStateAgo` | Wie lange vor dem Abbruch das letzte State-Update kam, in ms. Sekunden heißen, dass die Pakete schon vor dem Abbruch ausblieben |
| `lastPongAgo`, `ping` | Der letzte Pong und die letzte Round-Trip-Zeit |
| `missedStates` | Über die ganze Verbindung verpasste State-Updates |

```typescript
network.on('disconnect', (info: DisconnectInfo) => {
  if (!info.closedByClient)
    showReconnectDialog()
})
```

Der Client loggt das als eine Zeile, als Warnung, außer er hat die Verbindung selbst geschlossen, z. B. `Socket disconnected: connection disconnected (ice disconnected) after 312.4s, last state 6.1s ago, last pong 5.8s ago, ping 42ms, 3 states missed`. `describeDisconnect(info)` liefert diese Zeile. Der Server loggt jeden Abbruch mit dem Grund, wie lange die Verbindung bestand und wann er zuletzt vom Client gehört hat.
