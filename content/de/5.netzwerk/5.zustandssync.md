Zustandssynchronisierung ist der Prozess, durch den der Server bei jedem Tick den autoritativen Weltzustand an verbundene Clients sendet.

## Wie es funktioniert

1. **Server-Tick** — Bei jedem festen Tick (Standard 30/s) berechnet der Server die Physikwelt und aktualisiert alle Entities
2. **Serialisierung** — Der Zustand jeder Entity wird über `serialize()` (von `GameObject`) serialisiert
3. **Distanzfilterung** — Nur Entities innerhalb von `getStateSyncDistance()` eines bestimmten Clients werden in das Zustandspaket dieses Clients aufgenommen
4. **Senden** — Der gefilterte Zustand wird über den WebRTC-Socket an jeden Client gesendet
5. **Client anwenden** — Der Client ruft `updateFromNetwork(data)` auf jeder passenden lokalen Entity auf und erstellt unbekannte mit der [NetworkedEntityFactory](/de/netzwerk/vernetzte-akteure#networkedentityfactory)

## Was synchronisiert wird

- [Szenen](/de/kernkonzepte/szenen)-Objekte sind Map-Daten, die jeder Client selbst lädt, daher werden sie **nicht** gesendet — außer sie sind vernetzte Entities (`NetworkedGameObject`).
- Clients, die den [Level-Editor](/de/kernkonzepte/level-editor) ausführen, sind keine Spieler: Sie bekommen alle synchronisierten Entities der Welt, unabhängig von der Distanz.
- Wenn ein Spieler die Verbindung trennt, markiert der Server ihn mit `garbageCollect`; die Welt zerstört ihn im nächsten Tick, und Clients in der Nähe bekommen `SV_REMOVE_ENTITY`.

## Client-seitige Vorhersage

Clients wenden ihre eigenen Eingaben sofort an und senden sie mit `NetworkManager.sendCommand()`, das jeder eine Sequenz-ID gibt. Der Server wendet sie der Reihe nach an und sendet die `lastProcessedSequenceId` jedes Spielers im Zustand zurück. Der Client verwirft die bestätigten Eingaben mit `dropCommandsAtSequenceId()` und korrigiert seinen Spieler anhand des Server-Zustands. Siehe [NetworkManager](/de/netzwerk/client#reconciliation).

## Entfernungsbasierte Sichtbarkeit

Der Server sendet nur Zustand für Entities innerhalb eines konfigurierbaren Radius jedes verbundenen Clients. Dies reduziert die Bandbreite für große Welten.

```typescript
class MyServer extends Server {
  getStateSyncDistance(): number {
    return 150 // Nur Entities innerhalb von 150 Einheiten synchronisieren
  }
}
```

## Bandbreitenverfolgung

Überwache gesendete und empfangene Bandbreite mit dem eingebauten Tracker:

```typescript
server.bandwidthTracker // Auf Bandbreitenstatistiken zugreifen
```

Das [Dashboard](/de/werkzeuge/monitoring) zeigt sie live, pro Sekunde.

## Zustandspaket-Format

Jedes `SV_STATE` wird vom Server gestempelt, damit Clients und Tools Zustände auseinanderhalten können:

| Feld | Beschreibung |
|-------|-------------|
| `tick` | Nummer des Server-Ticks, in dem der Zustand erstellt wurde. Steigt pro Tick um eins, eine Lücke bedeutet also ein verlorenes Paket |
| `serverTime` | Epoch-ms auf dem Server, als der Zustand erstellt wurde |
| `ack` | Sequenz-ID der letzten Eingabe des Empfängers, die der Server vor diesem Zustand verarbeitet hat. `null` für einen Client ohne Spieler, wie den Editor |
| `entities` | Die `serialize()`-Ausgabe jeder Entity: ID, Position, Rotation, Zustands-Hash und beliebige benutzerdefinierte Felder |

Der Client hält die Stempel des letzten Zustands in [`NetworkManager.serverView`](/de/netzwerk/client#die-sicht-des-servers) fest.

Entities mit `garbageCollect === true` werden aus Zustandspaketen ausgelassen und der Client wird benachrichtigt, sie zu entfernen.

## Netzwerk-Debugging

In der Entwicklung zeichnen beide Seiten ihren Verkehr auf: jede Nachricht über den Spiel-Socket, die der Engine und deine eigenen, mit ihrer Größe, und Events wie:

| Event | Seite | |
|-------|------|---|
| `connect` / `disconnect` | beide | |
| `dropped` | beide | Der Transport hat eine Nachricht verworfen |
| `sync_enter` / `sync_leave` | Server | Entities, die in die Sync-Distanz eines Spielers kommen oder sie verlassen |
| `state_gap` | Client | Zustandsupdates, die nie angekommen sind |
| `state_out_of_order` | Client | Ein Zustand, der nach einem neueren angekommen ist |

Jede Seite behält ihre letzten 2000 Einträge und 8 MB ihrer Payloads. Der Server zeichnet auf, wenn `NODE_ENV` nicht `production` ist (`server.net`); ein Tab zeichnet auf, während die Dev-Bridge oder der Editor läuft (`network.net`, oder schalte es mit `network.net.enabled = true` ein). In einem Produktions-Build wird nichts aufgezeichnet und der Socket bleibt unangetastet.

`server.syncSnapshot()` sagt, wer was gesendet bekommt: die verfolgten Entities und das letzte Zustandsupdate jedes Spielers, und von wie vielen Spielern jede Entity verfolgt wird.

Ansehen kannst du es in:

- dem **Network**-Tab des [Dashboards](/de/werkzeuge/monitoring#network): Zustandsabgleich pro Spieler, Verkehr nach Nachricht und jedes Paket mit Payload;
- dem **Network**-Panel des [Editors](/de/kernkonzepte/level-editor#network-panel): Paketliste, Zeitleiste, Zustandsabgleich sowie Server-Ghosts und Sync-Radius-Ringe im Viewport;
- den Netzwerk-Tools des [MCP-Servers](/de/werkzeuge/ki-assistenten), für einen KI-Assistenten.

## Tick-Rate

Die Server-Tick-Rate bestimmt, wie häufig der Zustand gesendet wird. Standard ist **30 Ticks/Sekunde**, entsprechend gängigen Spielserver-Konventionen (sv_tickrate).

```typescript
const game = BaseGame.instance()
game.tickRate // 30 (Standard)
```

Um zu testen, wie sich dein Spiel bei einer schlechten Verbindung anfühlt, aktiviere die [Latenzsimulation](/de/netzwerk/server#latenzsimulation) des Servers.

Eine höhere Tick-Rate ergibt flüssigere Interpolation, erhöht aber Bandbreite und CPU-Auslastung.
