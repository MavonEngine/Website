Die Engine hat zwei Spielklassen, die dieselbe zugrunde liegende Schleife teilen: `BaseGame` (headless) und `Game` (Client mit Rendering).

## BaseGame

`BaseGame` ist der headless-Kern, der sowohl vom Server als auch vom Client verwendet wird. Es verwaltet:

- **Physikwelt** — Rapier3D `World`-Instanz
- **Character-Controller** — `KinematicCharacterController` für physikgesteuerte Bewegung
- **Szene** — Three.js `Scene` (zwischen Server und Client geteilt)
- **Tick-Rate** — Feste Update-Rate (Standard: 30 Ticks/Sekunde)
- **Welt** — `BaseWorld`-Instanz, die alle Entities verwaltet
- **Aktive Szene** — Die mit `loadScene()` geladene [Szene](/de/kernkonzepte/szenen) (`activeScene`)

Physikwelt und Character-Controller werden nur gesetzt, wenn du eine Rapier-Welt übergibst, siehe [Physik](/de/kernkonzepte/physik).

```typescript
import BaseGame from '@mavonengine/core/BaseGame'

class MyGame extends BaseGame {
  // ...
}

const game = MyGame.instance()
```

### Tick vs. Update

| Methode | Aufgerufen von | Zweck |
|--------|-----------|---------|
| `tick()` | Festes Intervall (tickRate) | Physik-Schritt, vernetzter Zustandsabgleich |
| `update(delta)` | Jedes Frame / Tick | Entity-Updates, Physiksimulation |

Jeder Tick löst `tickComplete` aus, mit seiner Dauer in Millisekunden.

### Update-Callbacks registrieren

```typescript
game.onUpdate((delta) => {
  // Bei jedem Frame/Tick mit Delta-Zeit in Sekunden aufgerufen
})

// Abmelden, wenn nicht mehr benötigt
game.unregisterOnUpdate(callback)
```

### Umgebungsprüfungen

```typescript
game.isDevMode()        // true wenn NODE_ENV !== 'production'
game.isProductionMode() // true wenn NODE_ENV === 'production'
```

## Game

`Game` erweitert `BaseGame` für den Client. Zusätzlich zu allem in `BaseGame` richtet es ein:

- **Canvas** — `HTMLCanvasElement`, in das das Spiel rendert
- **UI-Root** — `HTMLDivElement` für Overlay-UI
- **Größen** — Fenstergrößen-Tracking mit Resize-Behandlung
- **Kamera** — `PerspectiveCamera` mit `AudioListener`, in einem [Kamera-Rig](/de/kernkonzepte/vr#das-kamera-rig)
- **Renderer** — der `WebGPURenderer` von three.js (standardmäßig auf WebGL 2) mit Shadow-Mapping und einer Post-Processing-Pipeline, siehe [Renderer](#renderer)
- **Ressourcen** — Asset-Loader
- **InputManager** — Tastatur-, Maus- und [Gamepad](/de/eingabe#gamepads)-Eingabe
- **ParticleSystem** — Partikeleffekte
- **LoadingScreen** — Asset-Lade-Fortschrittsanzeige
- **Debug** — Tweakpane-Debug-Panel (aktiviert über `#debug`)
- **Editor** — In-Dev-Editor (nur im Dev-Modus)
- **Plugins** — Die mit `Game.usePlugins()` gesetzten [Engine-Plugins](/de/werkzeuge/plugins)
- **Netzwerk** — `game.network`, der `NetworkManager`, sobald einer erstellt wurde
- **Lokaler Spieler** — `game.localPlayer`, die Entity, die dieser Client steuert, falls dein Spiel sie setzt (wird von Dev-Tools verwendet)
- **XR** — `game.xr`, sobald [`enableXR()`](/de/kernkonzepte/vr) aufgerufen wurde

```typescript
import Game from '@mavonengine/core/Game'

const game = new Game(
  sources,         // Asset[], die beim Start geladen werden
  physicsWorld,    // optional RAPIER.World
  renderParameters // optional WebGPURendererParameters, z. B. { forceWebGL: false }
)
// Canvas und UI werden automatisch zu document.body hinzugefügt
```

### Render-Schleife vs. Tick

Die Render-Schleife läuft über die Animation-Loop des Renderers (`renderer.instance.setAnimationLoop`), die auch eine [WebXR-Session](/de/kernkonzepte/vr) antreiben kann, und rendert die Szene und die Partikel. Das `update(delta)` des Spiels — Eingabe, Physik, Entities, Plugins, Kamera — läuft auf dem festen Tick, genau wie auf dem Server. Eine begrenzte Framerate bremst die Simulation also nie aus:

```typescript
game.renderer.maxFps = 60 // 0 = jedes Frame rendern, in VR ignoriert
```

Was sich in jedem angezeigten Frame statt in jedem Tick bewegen muss, gehört auf `beforeRender`, das die Zeit seit dem letzten gerenderten Frame bekommt. Die Sicht im 30-Hz-Tick zu bewegen, während ein Display mit 60 - 120 Hz oder ein Headset läuft, lässt die Welt ruckeln:

```typescript
game.on('beforeRender', (delta: number) => {
  game.camera.place(behindPlayer, player.position)
})
```

Die Animationen von [`Entity3D`](/de/kernkonzepte/entity-system#entity3d) laufen dort weiter und spielen also mit der Rate des Displays.

### Renderer

`game.renderer.instance` ist der `WebGPURenderer` von three.js. Standardmäßig läuft er auf seinem WebGL-2-Backend, das auf denselben Geräten läuft wie bisher; mit `forceWebGL: false` in den Render-Parametern nutzt er WebGPU, wo der Browser es hat. `game.renderer.isWebGPU` sagt, welches läuft. In [TSL](https://github.com/mrdoob/three.js/wiki/Three.js-Shading-Language) geschriebene Materialien (Node-Materialien und [Material-Graphen](/de/kernkonzepte/material-graphen)) laufen auf beiden; das Gras, Wasser, der Regen und Rauch der Engine sind ebenfalls TSL.

```typescript
const game = new Game(sources, physicsWorld, { forceWebGL: false, antialias: true })
```

Die Szene rendert über eine `RenderPipeline` (`game.renderer.pipeline`), die den `EffectComposer` ersetzt. Post-Processing fügst du mit `addEffect()` hinzu: Jeder Effekt bekommt das bisherige Bild, angefangen mit `game.renderer.scenePass`, und gibt das neue zurück. Ein Effekt unter einem schon vergebenen Namen ersetzt den alten an seiner Stelle; die zurückgegebene Funktion entfernt ihn.

```typescript
import { bloom } from 'three/examples/jsm/tsl/display/BloomNode.js'

const remove = game.renderer.addEffect('bloom', input => input.add(bloom(input)))
game.renderer.effectNames // ['bloom']
```

In VR geht die Szene ohne die Pipeline direkt ans Headset, siehe [Rendern in VR](/de/kernkonzepte/vr#rendern-in-vr).

Für Frame- und GPU-Zeiten, Draw Calls, Speicher und Shader startet `game.renderer.attachInspector(container?)` den Inspector von three.js, `detachInspector()` beendet ihn. Der Schalter *inspector* im Debug-Panel und das [Performance-Panel](/de/kernkonzepte/level-editor#layout) des Editors tun dasselbe. Er ersetzt das three-perf-Panel, das [`mavonengine upgrade`](/de/werkzeuge/cli#mavonengine-upgrade) aus älteren Projekten entfernt. `game.renderer.frames` zählt die bisher gezeichneten Frames.

`game.clock` ist ein `THREE.Timer`, der einmal pro gerendertem Frame weiterläuft: `getDelta()` und `getElapsed()` liefern das ganze Frame über denselben Wert.

### Events

| Event | Wann |
|-------|------|
| `documentReady` | Canvas und UI-Root sind im Dokument |
| `sceneLoading` / `sceneLoaded` | Eine Szene wird / wurde geladen (auch bei Reloads) |
| `editorBoot` | Der Level-Editor ist gestartet |
| `tickComplete` | Ein Tick ist fertig, mit seiner Dauer in ms |
| `beforeRender` | In jedem gerenderten Frame, bevor er rendert, mit der Zeit seit dem letzten in Sekunden |
| `xrSessionStart` / `xrSessionEnd` | Eine [VR-Session](/de/kernkonzepte/vr) hat begonnen (mit der `XRSession`) / ist zu Ende |

## Singleton-Muster

Beide Klassen verwenden eine statische `instance()`-Methode. Rufe sie überall auf, um die vorhandene Instanz zu erhalten oder beim ersten Aufruf eine neue zu erstellen.

```typescript
const game = Game.instance()
// Gibt immer dieselbe Instanz zurück
```
