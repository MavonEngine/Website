MavonEngine verwendet [Rapier3D](https://rapier.rs/) (`@dimforge/rapier3d-compat`, 0.21) für die Physik. Die Engine erstellt die Physikwelt nicht für dich: Du erstellst eine `RAPIER.World`, übergibst sie, und die Engine berechnet sie bei jedem Tick und reicht sie an alles weiter, was sie braucht.

## Die Welt erstellen

Rapier ist ein WebAssembly-Modul, also rufe einmal `RAPIER.init()` auf, bevor du die Welt erstellst. Das Multiplayer-Template macht das auf beiden Seiten genauso.

### Server

Übergib die Welt an deinen `Server`. Er erstellt damit das headless `BaseGame`.

```typescript
// server/src/index.ts
import RAPIER from '@dimforge/rapier3d-compat'
import logger from './Logger'
import Server from './Server'

RAPIER.init().then(() => {
  const physicsWorld = new RAPIER.World({ x: 0, y: -9.83, z: 0 })

  // Statischer Boden
  const groundBody = physicsWorld.createRigidBody(RAPIER.RigidBodyDesc.fixed())
  physicsWorld.createCollider(
    RAPIER.ColliderDesc.cuboid(100, 0.5, 100).setTranslation(0, -0.5, 0),
    groundBody,
  )

  const server = new Server(logger, physicsWorld, { /* ServerOptions */ })
  server.start()
})
```

### Client

Übergib die Welt als zweites Argument von `Game`.

```typescript
// client/src/main.ts
import RAPIER from '@dimforge/rapier3d-compat'
import Game from '@mavonengine/core/Game'

RAPIER.init().then(() => {
  const physicsWorld = new RAPIER.World({ x: 0, y: -9.83, z: 0 })

  const game = new Game([/* assets */], physicsWorld)
})
```

Ohne Welt bleiben `physicsWorld` und `characterController` `undefined`, und es läuft kein Physik-Schritt. Für Spiele, die keine Physik brauchen, ist das völlig in Ordnung.

## Auf die Physikwelt zugreifen

Beide Seiten stellen dieselben zwei Eigenschaften an der Spielinstanz bereit:

| Eigenschaft | Typ | Beschreibung |
|----------|------|-------------|
| `physicsWorld` | `RAPIER.World \| undefined` | Die Welt, die du übergeben hast |
| `characterController` | `KinematicCharacterController \| undefined` | Aus der Welt erstellt, siehe [Character-Controller](#character-controller) |

### Aus geteiltem Code

`BaseGame.instance()` gibt das laufende Spiel auf der Seite zurück, auf der der Code gerade läuft: das headless Spiel des Servers oder das `Game` des Clients (das `BaseGame` erweitert). Code, der auf beiden Seiten laufen soll, wie die `Base/`-Entities des Templates, verwendet es:

```typescript
import type { Vector3 } from 'three'
import RAPIER from '@dimforge/rapier3d-compat'
import BaseGame from '@mavonengine/core/BaseGame'
import GameObject from '@mavonengine/core/World/GameObject'

export default class Crate extends GameObject {
  collider?: RAPIER.Collider

  constructor(position: Vector3) {
    super(undefined, position)

    const physicsWorld = BaseGame.instance().physicsWorld
    if (physicsWorld) {
      this.collider = physicsWorld.createCollider(
        RAPIER.ColliderDesc.cuboid(0.5, 0.5, 0.5).setTranslation(position.x, position.y, position.z),
      )
    }
  }

  destroy(): void {
    if (this.collider)
      BaseGame.instance().physicsWorld?.removeCollider(this.collider, false)
    super.destroy()
  }

  update(_delta: number): void {}
}
```

Prüfe auf `physicsWorld`, statt davon auszugehen, dass es existiert — so funktioniert die Klasse auch in einem Spiel ohne Physik.

### Auf dem Server

Innerhalb deiner `Server`-Unterklasse ist das Spiel `this.game`. Von überall sonst verwendest du `Server.instance().game` oder `BaseGame.instance()`; beide geben dasselbe headless Spiel zurück.

```typescript
import BaseServer from '@mavonengine/core/Networking/Server/Server'

export default class Server extends BaseServer<Player> {
  protected onTick(delta: number): void {
    const world = this.game.physicsWorld
    // z.B. autoritative Raycasts gegen die Collider des Servers
  }
}
```

```typescript
import Server from '@mavonengine/core/Networking/Server/Server'

const physicsWorld = Server.instance().game.physicsWorld
```

### Auf dem Client

```typescript
import Game from '@mavonengine/core/Game'

const game = Game.instance()
game.physicsWorld        // RAPIER.World
game.characterController // KinematicCharacterController
game.physicsDebugRender  // RapierDebugRenderer, siehe unten
```

## Physik-Schritt

Du rufst `physicsWorld.step()` nie selbst auf. `BaseGame.update()` setzt `physicsWorld.timestep` auf das Delta des Ticks, berechnet die Welt und aktualisiert dann die Entities der Welt und deine `onUpdate()`-Callbacks. Das läuft auf beiden Seiten auf dem festen Tick (`tickRate`, standardmäßig 30 pro Sekunde).

Auf dem Client ist der Physik-Tick vom Rendering getrennt: Eine mit `game.renderer.maxFps` begrenzte Framerate bremst die Physik nicht aus.

## Character-Controller

Wenn eine Welt übergeben wird, erstellt `BaseGame` einen `KinematicCharacterController` mit:

- einem Offset von `0.01`
- Impulsen, die auf dynamische Bodies angewendet werden, die er wegschiebt
- Einrasten auf den Boden bis `30`
- einem maximalen Steigungswinkel von 45°
- automatischem Rutschen an Hängen über 30°

Ändere ihn, nachdem das Spiel erstellt wurde, z.B. `game.characterController?.setMaxSlopeClimbAngle(60 * Math.PI / 180)`.

Der geteilte `Player` des Templates bewegt damit bei jedem Update einen kinematischen Body:

```typescript
const cc = BaseGame.instance().characterController
if (cc) {
  cc.computeColliderMovement(this.characterCollider, moveIntent)
  const move = cc.computedMovement()

  const pos = this.rigidBody.translation()
  this.rigidBody.setNextKinematicTranslation({
    x: pos.x + move.x,
    y: pos.y + move.y,
    z: pos.z + move.z,
  })
}
```

Weil dieselbe Klasse auf beiden Seiten läuft, bewegt der Server den autoritativen Spieler, und der Client sagt seinen eigenen Spieler mit identischer Physik voraus. Siehe [Netzwerk](/de/netzwerk), wie der Zustand des Servers den Client dann korrigiert.

## Server- und Client-Welten

Der Server und jeder Client haben ihre **eigene** Physikwelt; sie werden nicht synchronisiert. Collider existieren auf einer Seite, wenn der Code dieser Seite sie erstellt:

- **Geteilte Klassen** (das `server/src/Base/` des Templates, das der Client als `@template/server/Base/...` importiert) erstellen auf beiden Seiten dieselben Collider, z.B. die Kapsel des Spielers und die Bäume.
- **Szenenobjekte** werden pro Seite gebaut. Gib einem Szenenobjekt eine `server`-Factory, um seine Collider auf dem Server zu bauen, und eine `client`-Factory für den Client. Siehe [Szenen](/de/kernkonzepte/szenen).
- Der Server bleibt autoritativ: Nur was der Server simuliert, wird im Zustandsabgleich an die Clients gesendet.

Entferne, was du erstellst, in `destroy()`. Wenn du einen Rigid Body mit `removeRigidBody()` entfernst, werden auch die daran hängenden Collider entfernt.

## Debugging

Öffne das Spiel mit `#debug` (z.B. `http://localhost:8050/#debug`), um die Physikwelt des Clients als Wireframe-Linien zu zeichnen. Der Ordner **Physics** im Debug-Panel zeigt die Anzahl der Bodies, Collider und aktiven (wachen) Bodies.

```typescript
game.physicsDebugRender?.toggleVisible(false) // Collider-Overlay ausblenden
```

Auf dem Server melden das [Dashboard](/de/werkzeuge/monitoring) und der Endpunkt `/api/game/metrics` die Bodies und Collider der Server-Welt.
