State synchronization is the process by which the server broadcasts the authoritative world state to connected clients on each tick.

## How it works

1. **Server tick** — On each fixed tick (default 30/s), the server steps the physics world and updates all entities
2. **Serialization** — Each entity's state is serialized via `serialize()` (from `GameObject`)
3. **Distance filtering** — Only entities within `getStateSyncDistance()` of a given client are included in that client's state packet
4. **Broadcast** — The filtered state is sent to each client over the WebRTC socket
5. **Client apply** — The client calls `updateFromNetwork(data)` on each matching local entity, and creates unknown ones with the [NetworkedEntityFactory](/networking/networked-actors#networkedentityfactory)

## What is synced

- [Scene](/core-concepts/scenes) objects are map data every client loads itself, so they are **not** sent, unless they are networked entities (`NetworkedGameObject`).
- Clients running the [level editor](/core-concepts/level-editor) are no players: they get every synced entity in the world, regardless of distance.
- When a player disconnects, the server flags it with `garbageCollect`; the world destroys it on the next tick, and nearby clients get `SV_REMOVE_ENTITY`.

## Client-side prediction

Clients apply their own inputs right away and send them with `NetworkManager.sendCommand()`, which gives each one a sequence id. The server applies them in order and sends each player's `lastProcessedSequenceId` back in the state. The client drops the acknowledged inputs with `dropCommandsAtSequenceId()` and corrects its player from the server's state. See [NetworkManager](/networking/client#reconciliation).

## Distance-based visibility

The server only sends state for entities within a configurable radius of each connected client. This reduces bandwidth for large worlds.

```typescript
class MyServer extends Server {
  getStateSyncDistance(): number {
    return 150 // Only sync entities within 150 units
  }
}
```

## Bandwidth tracking

Monitor sent and received bandwidth with the built-in tracker:

```typescript
server.bandwidthTracker // Access bandwidth stats
```

The [dashboard](/tooling/monitoring) shows it live, per second.

## State packet format

Each entity contributes its `serialize()` output to the state packet. The format is:
- Entity ID (key)
- Serialized state (value) — position, rotation, state hash, and any custom fields

Entities with `garbageCollect === true` are omitted from state packets and the client is notified to remove them.

## Tick rate

The server tick rate controls how frequently state is sent. Default is **30 ticks/second**, matching common game server conventions (sv_tickrate).

```typescript
const game = BaseGame.instance()
game.tickRate // 30 (default)
```

To test how your game feels on a bad connection, enable the server's [latency simulation](/networking/server#latency-simulation).

A higher tick rate gives smoother interpolation but increases bandwidth and CPU usage.
