The `Server` class is the authoritative multiplayer server. It creates the headless `BaseGame`, manages client connections, processes commands, broadcasts world state, and serves the game client and its HTTP API.

## Setup

```typescript
import type { ServerChannel } from '@geckos.io/server'
import BaseServer from '@mavonengine/core/Networking/Server/Server'
import Player from './Server/Entities/Player'

export default class Server extends BaseServer<Player> {
  protected onConnection(channel: ServerChannel): Player {
    // A new client connected: return its player, the server adds it to the world
    return new Player(channel.id)
  }

  protected onCommand(command: any, delta: number): void {
    // Process an incoming client command
  }

  getStateSyncDistance(): number {
    // Return the visibility radius (units) for state sync
    return 200
  }
}
```

```typescript
import RAPIER from '@dimforge/rapier3d-compat'

RAPIER.init().then(() => {
  const physicsWorld = new RAPIER.World({ x: 0, y: -9.83, z: 0 })

  const server = new Server(logger, physicsWorld, {
    client: { root: clientDir, dev: process.env.MAVONENGINE_DEV_CLIENT === '1' },
    plugins: { root: projectRoot },
  })

  server.start().then(() => server.openScene('main'))
})
```

The constructor takes a winston logger, an optional Rapier world (see [Physics](/core-concepts/physics)) and the options below. Inside the server, the game is `this.game`; elsewhere use `Server.instance()`.

`start()` returns a promise: with `plugins: { root }` the plugins are imported first, so wait for it before relying on them.

## Options

| Option | Default | Description |
|--------|---------|-------------|
| `httpPort` | `8050` | Port of the HTTP server |
| `client` | | Serve the game client: `{ root, dev?, dist? }`. With `dev` the source is served through Vite with hot reload, otherwise the built `<root>/dist` |
| `socketPort` | none when `client` is set, `8081` otherwise | Separate port for the geckos.io game socket, or `false` |
| `plugins` | | `{ root }` to load the plugins enabled in `<root>/mavonengine.json`, or plugin objects. See [Plugins](/tooling/plugins) |
| `root` | `plugins.root` | Project root with `scenes/`, used by `openScene()` |
| `metrics` | | `{ enabled, token, logBufferSize, requestLogSize, logIntervalMs }`, see [Monitoring](/tooling/monitoring) |
| `latencySimulation` | | `{ fixedLatency, jitter, packetLoss }`, see [Latency simulation](#latency-simulation) |

## Ports

When the server serves the client, everything runs on **one port** (`8050` by default): the client, the game socket and the HTTP API. The client needs no second origin, which makes deploying behind a reverse proxy simple.

| Port | Purpose |
|------|---------|
| `8050` | HTTP server: client, API and the game socket |
| `8081` | Separate geckos.io socket, only when the client is not served or `socketPort` is set |

## Methods to implement

| Method | Description |
|--------|-------------|
| `onConnection(channel)` | Called when a new client connects; return its player entity |
| `onCommand(command, delta)` | Called for each queued command on each tick |
| `getStateSyncDistance()` | Returns the max distance for state sync visibility |
| `onTick(delta)` | Optional, runs every tick after the commands are processed |

## Command buffer

Clients send commands (e.g. input frames) with a sequence id. The server queues them, sorts them by sequence id and processes them in order on each tick via `onCommand`. After a command ran, the player's `lastProcessedSequenceId` is updated and sent back in the state sync, so the client can drop the inputs the server has already applied.

## Scenes

```typescript
server.openScene('main')               // <root>/scenes/main.json
server.openScene('main', { watch: true })
```

Only the scene objects with a `server` factory are built. While the client is served through Vite, the file is watched and reloaded when the [editor](/core-concepts/level-editor) saves it. See [Scenes](/core-concepts/scenes).

## Editor clients

A client that boots the level editor tells the server. The server removes its player, no longer counts it as a player and sends it every entity in the world. Their channel ids are in `server.editorChannels`.

## HTTP endpoints

Register custom HTTP routes using `onHttp` before calling `start()`:

```typescript
server.onHttp((app) => {
  app.get('/api/status', (req, res) => {
    res.json({ players: server.game.world.entities.items.size })
  })
})
```

Your routes run before plugin routes and before the game client, which answers every remaining page request.

Built-in endpoints:

| Path | Description |
|------|-------------|
| `GET /api/game/health` | Health check |
| `GET /api/game/metrics` | Metrics snapshot (tick time, CPU, bandwidth, players, world, physics) |
| `GET /api/game/logs` | Recent server log entries |
| `GET /api/game/requests` | Recent HTTP requests |
| `GET /api/game/dev/*` | Scene and entity inspection, development only |

The metrics, logs and requests endpoints only answer localhost unless a token is set. See [Monitoring](/tooling/monitoring).

## Latency simulation

Test your netcode against a bad connection. The server delays pongs, state updates and incoming commands:

```typescript
const server = new Server(logger, physicsWorld, {
  latencySimulation: {
    fixedLatency: 100, // ms
    jitter: 30,        // ms
    packetLoss: 0.05,  // 0 - 1
  },
})
```

The server logs a warning on start while the simulation is on. Never ship it enabled.

## Bandwidth tracking

The server tracks sent and received bandwidth. Access it via `server.bandwidthTracker`, or all metrics via `server.metrics`.

## ServerWorld

The server's world is a `ServerWorld`, which extends `BaseWorld` and adds player management for connected clients (`world.players`).

The server maintains its own Three.js scene populated with **simplified hitbox meshes** rather than full visual geometry. This keeps memory and CPU overhead low while still allowing authoritative raycasts, hit detection, and spatial queries directly against the scene — no need to trust client-reported positions.

## Stopping

`server.stop()` stops the metric timers, the scene watcher and the plugins.
